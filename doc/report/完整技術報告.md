## 摘要

這是一個涵蓋資料擷取、清洗、情緒分析、資料庫設計、特徵工程、機器學習
與 BI 視覺化的端到端（End-to-End）金融情緒與股價趨勢預測系統。

專案的起點是一個常見假設：股市討論區的情緒能否用於預測股價漲跌。系統
完成後，四個模型對「明天會漲還是會跌」的判斷能力，AUC 約落在 0.50
（AUC 衡量模型能否將會漲與會跌的樣本正確排序，0.50 代表沒有排序能力，
1.0 代表完全正確），接近隨機判斷。

進一步拆解不同預測目標後發現：模型雖然無法判斷漲跌方向，卻能有效辨識
「這筆交易在觀察期間內是否會觸及設定的漲跌障礙」（技術上稱為 Timeout，
即觀察期間內價格未觸及任何一側障礙）。這項發現使產品方向由「預測
漲跌」調整為「判斷是否適合進場」。該判斷模型在反覆用於調整方法的資料
段上，於保留八成以上交易機會的前提下，將精準度提升至隨機基準的 4 倍；
在完全未使用過的最終驗證資料上重新測試後，精準度提升倍數上升至約
10 倍——此提升主要源於該資料段本身 Timeout 發生率較低，而非模型表現
改善，詳見第 9.11 節；該發生率在此驗證期間內逐折下降至個位數樣本，
逐折數字見新增的第 9.11.1 節。

同一份驗證資料上，另外測試了一條不訓練任何模型、僅依當日波動率高低
判斷的簡單規則，其效果與整套機器學習管線相近。這代表目前尚無法判定
該機器學習管線相較於簡單規則所創造的邊際價值，此問題留待下一階段
（`UG-Gate-4`）評估，本報告不做裁決。

本報告的目的除了說明系統的實作內容，也記錄驗證過程本身：每一項數字
皆附可查核的證據來源，尚未驗證或存在不確定性之處，均如實標注。

# 第 1 章　專案定位與問題陳述

## 1.1 要解決什麼問題

專案目標是打造一個自動化的資料管線：整合官方股價 API 與網路論壇（PTT
股票板）的情緒討論，透過機器學習輔助分析股價未來趨勢，並用互動式儀表板
（Streamlit＋Plotly）呈現。核心價值在於展示處理異質資料源（官方 API ＋
網路爬蟲）、資料清洗、資料庫設計、機器學習應用，以及具備容錯機制的自動化
ETL（Extract-Transform-Load，資料擷取—轉換—載入三段式管線的統稱）流程的
綜合工程能力。
（來源：`doc/spec/PRD_Financial_Sentiment_System_v1.md` v2 §1）

## 1.2 為什麼選這個題目

這個題目刻意把三種不同性質的技術棧放進同一條管線裡：官方結構化 API（股價）、
非結構化網路爬蟲（論壇文章）、以及大型語言模型（LLM）輔助的文字理解。三者
的失敗方式完全不同——API 可能回傳延遲但格式穩定，爬蟲可能被網站結構變動
或防爬機制擋下，LLM 可能因為額度限制或回應格式不穩定而失敗。一個能同時
處理這三種失敗模式、還能保持資料一致性的系統，比只處理單一乾淨資料源的
系統更接近真實產業場景。

## 1.3 系統邊界：做什麼、不做什麼

**做的事**：資料擷取與清洗、情緒分析、特徵工程、時序機器學習、以及一個
可以呈現以上所有結果的儀表板。

**明確不做的事**：

- **不下單、不接券商 API**——系統只產出判斷，不執行交易。
- **不宣稱任何獲利能力**。評估用的策略報酬、Sharpe ratio（夏普比率，
  衡量「每承擔一單位風險換得多少報酬」的指標，數字越高代表相同風險下
  賺得越多）等指標程式碼確實存在（`src/ml/evaluator.py`），但**沒有任何
  一份證據檔記錄過通過樣本外驗證的損益數字**，也沒有計入手續費、滑價
  等真實交易成本，因此本報告不提出任何獲利宣稱（詳見第 13.2 節）。
- **不做完整的交易模擬與淨累積報酬計算**——這是明確登記在案、留給後續
  階段的候補案（`PROJECT_STATUS.md` §0.5、`UG-G3-SB7` Gate B §10）。

# 第 2 章　系統架構總覽

## 2.1 五層架構

系統由五層構成，資料單向流動：

```
擷取層 (Extractors)  →  轉換層 (Transform)  →  載入層 (Loaders)
     ↓                                                ↓
  外部資料來源                              PostgreSQL 資料庫
                                                       ↓
                              機器學習層 (ML)  →  視覺化層 (UI)
```

| 層 | 目錄 | 責任 |
|---|---|---|
| 擷取層 | `src/extractors/` | 向外部取得原始資料（官方股價 API、PTT 論壇、AI 熱門詞探索） |
| 轉換層 | `src/transform/` | 資料清洗、NLP 情緒分析、特徵工程 |
| 載入層 | `src/loaders/` | PostgreSQL 讀寫 |
| 機器學習層 | `src/ml/` | 時序切分、多模型訓練、Timeout Gating 判斷 |
| 視覺化層 | `src/ui/` + `app.py` | Streamlit 儀表板 |

`main_etl_pipeline.py` 負責串接擷取、轉換、載入三段的執行流程（第
6 章詳述執行順序與失敗處理）。

> ⚠ **命名提醒**：本報告所有「Gate」皆指現行升級計畫的 `UG-Gate-0～4`
> （見 `doc/upgrade/`）。專案內部的 `doc/spec/SDD_*.md` 文件裡另外記載著
> 一組**前任團隊、與本計畫無關**的舊 Phase Gate（現已在 SDD v2 中正名為
> **Legacy Phase Gate 2～5**，於 2026-08-20 由前一任負責人關閉，連內部子項
> 編號都與 `UG-Gate` 系統重複但內容完全不同）。全文提到 Gate 時一律使用
> 全名 `UG-Gate-N`，避免與這組歷史記錄混淆。

## 2.2 各層模組責任

模組分層（extractors／transform／loaders／ml／ui）自 `UG-Gate-1` 定案後
沒有變動；`UG-Gate-2`、`UG-Gate-3` 都是在既有分層下新增模組（例如
`src/ml/gating.py`、`src/ml/calibration.py`），沒有推翻既有架構。
（來源：`doc/spec/SDD_Financial_Sentiment_System_v1.md` v2）

## 2.3 技術選型與理由

| 選了 | 沒選 | 理由 |
|---|---|---|
| 編號式 SQL migration（遷移腳本）＋ `schema_version` 表 | Alembic（Python 資料庫遷移框架） | 目前只有 9 個遷移腳本，規模下額外抽象層不划算；`DB_MIGRATION_PLAN.md` 明訂超過 10 個腳本再重新評估 |
| 自製排程 daemon（`scheduler.py`） | APScheduler、cron | 零額外相依套件；30 秒輪詢設計可抵抗系統休眠造成的時鐘漂移 |
| `unittest`（Python 內建測試框架） | pytest | 開發環境裡沒有安裝 pytest；這是環境限制，不是刻意的技術選擇 |
| 純 NumPy 手刻評估指標 | 直接依賴 `sklearn.metrics` | 讓 Accuracy、F1、AUC 等指標在缺少 `scikit-learn` 的降級環境下仍可執行與測試 |

## 2.4 開發環境與可重現性

開發在 VS Code Dev Container 中進行（Python 3.14.6 ＋ PostgreSQL 18），
Windows host 是輔助環境、非正式測試環境（host 缺少 `sklearn`／`lightgbm`／
`xgboost`／`psycopg2` 等套件，這些路徑在 host 上會走程式內建的簡化替代
實作，因此 host 上的測試結果**不能**用來支持任何機器學習、NLP 或資料庫
相關的宣稱）。

環境釘選分三層：

1. **基底映像**：以 SHA256 digest 釘選 Docker 基底映像，避免上游映像
   更新時無聲改變環境。
2. **Python 套件**：`requirements.lock.txt` 記錄精確版本（含所有間接
   相依套件），這是重現基線的依據；`requirements.txt` 只是意圖清單，
   多數項目沒有版本上界。
3. **安裝身分**：容器內以非 root 使用者（`vscode`）安裝套件——以 root
   安裝會裝進系統路徑，之後以一般使用者身分執行時會顯示「全部套件
   缺席」，此問題在專案早期實際發生過一次。

`VERIFIED THIS SESSION`（`CLAUDE.md` §13.6 記載的一次淨重建驗證）：用
全新、獨立於開發容器的拋棄式容器重跑，測試結果與基線一致，`pip freeze`
輸出的 87 個套件版本逐行完全相同，確認環境可重新建置。

# 第 3 章　資料擷取層：異質來源與失敗語意

## 3.1 九個擷取模組

`src/extractors/` 目錄下有 9 個模組，分工如下：

| 模組 | 職責 |
|---|---|
| `market_report_fetcher.py` | 全市場批次股價擷取（見 3.2 節） |
| `market_report_table.py` | 兩個市場報表共用的表格解析邏輯 |
| `twse_market_report.py` | 台灣證交所（TWSE）全市場日報表解析 |
| `tpex_market_report.py` | 櫃買中心（TPEx）全市場日報表解析 |
| `ptt_scraper.py` | PTT 股票板爬蟲（含留言解析） |
| `twse_scraper.py` | 舊版逐檔股價擷取（已被 3.2 節的批次方式取代，去留待決） |
| `yfinance_api.py` | 美股（NVDA）股價擷取 |
| `trend_discover.py` | 用 LLM 從 PTT 熱門文章標題探索新的追蹤關鍵字 |
| `retry_policy.py` | 全站共用的重試判斷邏輯（見 3.5 節） |

本專案沒有整合 FinMind 或其他第三方金融資料平台——股價資料完全來自
官方交易所報表與 `yfinance`（Yahoo Finance 的 Python 套件）。

## 3.2 全市場批次擷取：把 150 個請求變成 1 個

早期的做法是「逐檔股票各打一次 API」——追蹤 150 檔股票就要發 150 次
請求。`market_report_fetcher.py` 改成向交易所要**當天全市場的日報表**
（TWSE 的 `MI_INDEX` 報表、TPEx 的日成交資訊），一次請求拿到當天所有
掛牌股票的資料，再從中篩出需要的。

`VERIFIED THIS SESSION`（`twse_market_report.py` 模組文件記錄的一次
實測）：2026-08-21 該日報表共 32,751 列，篩出 1,085 檔屬於普通股（排除
ETF、權證等）的候選列。每天只需對每個市場發 1 次請求，總請求數固定
為 2 次（兩個市場各一次），不再與追蹤檔數成正比。

## 3.3 多來源資料契約

系統設計上允許未來接入多個社群討論來源（目前只有 PTT 一個實際在運作，
Dcard 已嘗試但失敗，見 3.7 節），因此需要一份契約規範「不同來源怎麼
匯入同一張表」。契約的核心原則：

- 每個來源各自寫一個獨立的 Adapter（轉接器），輸出對齊到共用的
  `market_articles` 表結構。
- 各來源特有的欄位（例如 PTT 的推／噓／箭頭統計，或未來 Dcard 的愛心數）
  各自保留獨立欄位，不強行壓成一個通用的「互動指標」——因為不同平台的
  互動機制在統計意義上不是同一件事，硬湊在一起會扭曲數字。
（來源：`doc/upgrade/contracts/MULTI_SOURCE_DATA_CONTRACT.md`）

## 3.4 三態失敗語意：抓不到資料 ≠ 真的沒有資料

這是整條資料品質防線的地基。系統把「來源出問題」拆成三種狀態，而不是
簡單的「有資料／沒資料」二分法：

| 狀態 | 意義 |
|---|---|
| `SUCCESS_EMPTY` | 正常取得來源回應，當天無新資料（例如休市日） |
| `SOURCE_DEGRADED` | 來源**部分**回應異常（例如某些欄位缺漏），但整體還能用 |
| `SOURCE_FAILED` | 來源完全連不上或回傳錯誤，代表無法判斷是否有資料，而非確認沒有資料 |

這三種狀態**在設計上**會一路往下傳遞到最終的 `daily_ml_features` 表的
`source_status` 欄位（見第 7 章），確保機器學習模型在訓練時能分辨
「這天真的沒人討論」和「這天爬蟲掛了、我們不知道有沒有人討論」——如果
把兩者混為一談，模型會把「爬蟲掛掉的那天」錯誤地學成「沒有情緒訊號的
那天」。

> ⚠ 誠實揭露：截至資料截止日（2026-09-16），`source_status` 欄位實際
> 只出現過 `SUCCESS` 與 `SUCCESS_EMPTY` 兩態——`SOURCE_FAILED` 的生產
> 呼叫端接線與 `SOURCE_DEGRADED` 的可達性，在當時都屬未完成項
> （`src/transform/feature_aggregator.py` 程式註解明寫「`SOURCE_DEGRADED`
> 仍不可達」）。三態的定義與資料庫欄位都已就緒，但只完成了「定義」，
> 沒有完成「全部三態都被寫入過」。`SOURCE_FAILED` 的接線已於截止日後
> 完成並首次真實寫入，見附錄 G。

## 3.5 重試紀律：用「有沒有拿到狀態碼」做分類，不是用例外類別名稱

`DEC-032`（已 APPROVED）訂下的判準很直白：

- **對方明確拒絕**（HTTP 4xx，含 403／429，代表「問題出在我們這端的
  請求，重試同一個請求不會讓它變對」）→ **不重試**，直接記為失敗。
- **對方沒答上來**（5xx 伺服器錯誤、連線逾時等傳輸層問題）→ **有限次數
  重試**。

這條「能不能重試」的判斷邏輯集中寫在共用函式
`src/extractors/retry_policy.py::is_retriable()`，全站呼叫同一套規則
判斷 Y／N——但**重試幾次、每次間隔多久，是各個呼叫端自己決定**，
`retry_policy.py` 本身不管這件事：`market_report_fetcher.py` 用 5 次、
退避 5→10→20→40→60 秒；`ptt_scraper.py` 用 tenacity 套件、3 次、
指數退避 2～10 秒；`twse_scraper.py` 同樣用 tenacity、3 次。共用的是
「值不值得重試」的判準，不是重試的節奏，這是刻意的分工——不同來源的
延遲特性不同，重試節奏本來就該各自決定。`yfinance_api.py` 的程式
註解裡誠實記錄了一個例外：`yfinance` 套件本身會把 HTTP 狀態碼吞掉，
讓程式碼**沒有能力**判斷是 4xx 還是 5xx，因此這條路徑選擇「不重試，
一律記為失敗」——這是主動標記出來的已知限制，不是被忽略的缺口。

## 3.6 ETL 執行紀錄四態

每一次擷取任務的結果都寫進 `etl_run_log` 表，結果只會是四種之一：
`OK`（成功）、`NO_DATA`（真的沒有資料）、`FETCH_FAILED`（擷取失敗）、
`REFUSED`（被明確拒絕，如 403／429）。這張表讓「這次任務到底發生了
什麼事」變成可查詢的資料，而不必事後翻 log 檔案猜測。

## 4.3 冪等性策略：每張表各自論證過，不是套一個公式

冪等性（Idempotency）指「同一個操作重複執行多次，結果應該跟只執行一次
一樣」——對 ETL 來說，代表「今天的擷取任務不小心跑兩次，資料庫裡的
資料不應該變成兩份或被錯誤覆寫」。多數系統對這件事只有一種寫法，本
系統則是逐表判斷「重複寫入時該怎麼處理」：

| 表 | 寫入策略 | 為什麼 |
|---|---|---|
| `candidate_prices` | 衝突時不覆寫（`DO NOTHING`） | 已收盤的歷史事實不該被改寫 |
| `stock_prices` | 衝突時覆寫，**含來源欄位** | 刻意讓來源紀錄跟著更新，避免血緣資訊過時 |
| `market_articles` | 衝突時不覆寫（URL 唯一） | 文章內容不會變 |
| 留言數更新 | 用獨立的 `UPDATE` 語句 | 永遠不跟新增文章的邏輯混在一起 |
| `daily_ml_features` | 衝突時覆寫，**但排除標籤欄位** | 特徵計算管線不能覆寫它自己沒有算出來的標籤（詳見下方 CHAL-010） |
| Triple-Barrier 標籤尾段重算 | 用純 `UPDATE`（不是 upsert） | 找不到對應列時要報錯，而不是生出一列殘缺資料 |

**CHAL-010（一個真實抓到的 bug）**：每日特徵更新原本用的寫法會把
`daily_ml_features` 的每一欄都覆寫一遍，包含它自己根本沒有算的
Triple-Barrier 標籤欄——意思是特徵管線每跑一次，前一天已經算好的
交易標籤就會被清空。修法是把標籤欄位排除在特徵管線的覆寫範圍外，
讓「算特徵」和「算標籤」互不干擾。

## 4.5 破壞性操作防護

`database/db_target_guard.py::assert_safe_migration_target()` 會在
遷移腳本建立資料庫連線**之前**檢查連線目標，如果偵測到目標疑似是真實
開發資料庫（而非明確標示的臨時測試資料庫），會直接中止、不建立任何
連線。這道防線**只保護遷移／驗證腳本**，不覆蓋日常寫入用的 `DBWriter`

防線，日常 ETL 就永遠跑不起來。這個不對稱是刻意設計，且在
`REMAINING_RISKS.md`（RISK-013）裡誠實記載這個防護範圍的邊界。

# 第 5 章　NLP 情緒管線：成本與正確性的取捨

## 5.1 三階段 Hybrid 管線

把一篇論壇文章標題轉換成一個情緒分數，系統用三段式管線：

1. **SnowNLP 初篩**：用開源中文情緒分析套件 SnowNLP 先對**全部**標題
   打一次分數（0～1 之間）——分數已經很極端（明顯正面或負面）的標題
   直接採用這個結果，不會進到下一步。
2. **快取比對**：只有落在**模糊區間（0.4～0.6）**的標題，才去查
   `sentiment_cache` 表，看這個標題是不是已經算過分數。
3. **Gemini LLM 精算**：模糊區間裡快取沒命中的標題打包成一批，呼叫
   Gemini（Google 的大型語言模型）取得更精確的判斷，結果寫回快取供下次
   重複使用。

`VERIFIED`（`doc/upgrade/gates/evidence/PRE_G3_03_scoring_result.json`）：
一次實際執行中，1,250 篇文章完成評分，只呼叫了 **3 次** LLM——但這次
執行**開始前 `sentiment_cache` 是 0 列**，也就是這 3 次呼叫**沒有靠
任何快取命中省下來**。真正把成本壓低的是 SnowNLP 初篩：1,250 篇裡只有
148 篇（約 11.8%）落在模糊區間，這 148 篇分三批（58、61、29 篇）送給
Gemini，對應剛好 3 次呼叫；執行完成後 `sentiment_cache` 才新增
135 列，供**未來**的執行重複使用。本次 LLM 成本的降低來自 SnowNLP
篩掉絕大多數標題、僅將約一成真正模糊的標題送入批次呼叫；快取命中
帶來的成本節省要到後續重複遇到同樣標題時才會顯現。

## 5.2 LLM 回應的防禦性驗證

呼叫 LLM 拿回來的 JSON 不能直接當作可信輸入使用，管線做了三層檢查：
拒絕重複出現的 ID、確認回傳的 ID 集合與送出去的候選完全一致、確認每個
分數都是 0～1 之間的有限浮點數。所有分數都在本地端算完、驗證通過後才
會去更動資料表，確保一次失敗不會留下寫到一半的殘缺結果。

## 5.3 檢查點設計：一個查詢語句就是檢查點

情緒評分是分批處理的（`batch_size=500`），系統沒有另外建一張「進度表」
記錄做到哪裡，而是直接用 `SELECT ... WHERE sentiment_score IS NULL
LIMIT 500` 這個查詢——只要一篇文章的分數欄位還是空的，代表它還沒被
處理過。這個設計讓「程式崩潰後重新啟動」這件事天然地從斷點接續，不需要
額外的狀態管理邏輯。

**CHAL-001（一個真實發生過的問題）**：早期版本的檢查點推進邏輯，會在
工作尚未真正完成的情況下就把進度往前推——中途發生錯誤時，重新啟動後
該批資料會被永久跳過，且輸出結果與正常完成時無法區分。修法為「只有
確實成功寫回資料庫，才能推進」，此原則已寫入專案的工程規範
（`CLAUDE.md` §7.2）：批次檢查點只有在一筆工作確實成功完成後才能
推進。

## 5.4 429 限流處理

Gemini API 偶爾會回傳 429（請求過於頻繁）。系統實作了零額外套件依賴的
指數退避（Exponential Backoff，即每次重試的等待時間逐次拉長，降低
連續請求頻率）：2 秒 → 4 秒 → 8 秒 → 16 秒，最多重試 5 次，且僅在
錯誤訊息符合暫時性特徵時重試（例如包含 "429"、"quota"、"rate
limit" 等字樣），而非遇到任何錯誤都重試。

> 此重試策略截止資料截止日為止未涵蓋「每日配額耗盡」這種情況——
> 截止日後已新增獨立判斷與 `REFUSED` 語意，見附錄 G。

## 5.5 題材情緒溢出加權

當一檔冷門股票當天沒有直接的討論文章時，系統會用它所屬題材（例如
「矽光子」概念股）的整體情緒分數補位：直接個股情緒佔 70%、題材溢出
情緒佔 30%；若某天完全沒有個股討論，則 100% 採用題材溢出分數。**刻意
不對留言數套用這套加權**——留言數是一個計數指標，題材層級的討論熱度
不能直接套用到個股上，否則會製造出不存在的討論量。

# 第 6 章　ETL 編排、排程與維運

## 6.1 七階段每日流程

`main_etl_pipeline.py` 的 `ETLPipelineManager.run_all_daily_tasks()`
依序執行：

0. 全市場批次股價擷取（第 3.2 節）
1. 追蹤名單個股價格更新
2. AI 熱門詞探索
3. PTT 論壇擷取
4. NLP 情緒評分（第 5 章）
5. 特徵工程（第 7 章）
6. Triple-Barrier 標籤尾段重算（第 8 章）

## 6.2 單一來源失敗不中斷其他階段

如果階段 0 的某個市場回傳 403（被拒絕），系統**不會**因此中止整條管線
——它會把這個失敗記錄為 `REFUSED`，其餘所有階段照常執行完畢，**最後**
才把這個例外重新拋出，讓程式以非零狀態碼結束。這個順序的用意是：先確保
「發生了什麼事」被完整寫進資料庫的稽核紀錄，再讓程式真正失敗——如果
反過來（先失敗、稽核紀錄沒寫完），事後會查不出當天到底發生了什麼。

## 6.3 批次完整性斷言

`etl_run_log.py::assert_complete()` 會確認「記錄下來的執行結果數量」
跟「原本應該處理的項目數量」相等，如果不相等就拋出 `IncompleteBatchError`
——這道檢查防止「有些項目悄悄被漏掉，卻沒有人發現」的情況發生。

## 6.4 排程器

`scheduler.py` 是一個自製、不依賴額外排程套件的常駐程式，設定在每個
交易日下午 3:35（台股收盤後）觸發。程式註解原話：「每 30 秒檢查一次，
以防止系統休眠喚醒造成的時間漂移」。`INFERENCE`：這樣設計是為了避免
「單純睡眠到預定時間」在系統休眠期間被跳過整段——電腦若在排程觸發
時間點前後被關機或休眠，喚醒後單純的睡眠等待可能直接錯過那個時間窗，
而 30 秒輪詢能在喚醒後很快偵測到「現在已經過了應該觸發的時間」並補跑；
這個因果推論在程式碼裡沒有被逐字寫出來，是本報告依註解與程式行為
推導的解讀。

**已知限制**：排程只用「星期幾」判斷是不是交易日（`weekday() < 5`），
沒有串接真正的交易所假日行事曆。遇到國定假日仍會嘗試執行，只是當天
沒有新資料，會被正確記錄為 `NO_DATA`。

## 6.5 時區事故

開發容器內部時鐘走 UTC（世界協調時間），但台北時間是 UTC+8。這個落差
曾造成一個不容易察覺的錯誤：系統看起來像是「留言比文章早了 4 小時被
抓到」——資料本身沒有損壞，但**時間先後順序被顛倒了**，而時間順序正是
整個機器學習防洩漏設計（第 8 章）最在意的事。修法是把所有跟業務邏輯
有關的「現在時間」統一改走 `src/common/clock.py::now_taipei()`，並用
測試（`test_timezone_policy.py`）掃描程式碼，確保生產程式碼裡不會再
出現沒有標明時區的「現在時間」寫法。

# 第 7 章　特徵工程與特徵契約

## 7.1 19 個工程特徵的三個家族

`daily_ml_features` 的 29 欄裡，扣掉識別欄位、中繼資料欄位與目標欄位，
真正拿去訓練模型的「工程特徵」共 19 欄，分三個家族：

| 家族 | 欄位數 | 內容 |
|---|---|---|
| 價量特徵 | 8 | 報酬率、RSI（相對強弱指標，衡量近期漲跌力道的技術指標）、5日／20日波動率、振幅比、均線乖離率、成交量比 |
| 社群情緒特徵 | 8 | 文章數、情緒均值、看多指數、一致性指數、3日／5日情緒均線、情緒滯後值 |
| 留言衍生特徵 | 3 | 留言量比、留言分歧度、推噓動能——**狀態為「規劃中」，尚未真正啟用**（見 7.6 節） |

## 7.2 兩個有學術出處的特徵

`bullishness_index`（看多指數）與 `agreement_index`（一致性指數）出自
Antweiler & Frank（2004）這篇研究論文，公式分別是：

- 看多指數 = `ln((1+正面篇數)/(1+負面篇數))`：正面討論相對負面討論
  越多，此值越大（越接近正無窮），完全沒有討論時值為 0。
- 一致性指數 = `1 - sqrt(1 - ((正面-負面)/(正面+負面))²)`：討論方向
  越一致（幾乎全正面或全負面），此值越接近 1；正負意見勢均力敵時，
  此值接近 0。

`INFERENCE`：這兩個公式來自學術文獻，不代表它們在本專案的資料上已經
被證實有預測力——研究證據與本專案的實測結果是兩件分開陳述的事（詳見
第 9 章，方向預測的實測結果顯示這些特徵在目前的資料覆蓋率下無法被
證實有效）。

## 7.3 版本化特徵契約

特徵集合本身有版本演進：

- **`LEGACY_17`**（契約標記「現行、待淘汰」）：17 個模型輸入，包含開
  高低價（OHL）本身作為輸入。
- **`CORE_16`**：拿掉開高低價，把收盤價／成交量降級為背景資訊（不直接
  餵給模型），改用比值型特徵（振幅比、均線乖離率、成交量比），原因見
  7.4 節。
- **`COMMENT_ENHANCED_19`**：在 `CORE_16` 基礎上加入 3 個留言衍生特徵。

`UG-Gate-3`（第 9 章的全部模型結果）實際訓練用的是以 `CORE_16` 為基礎
的兩個對照臂，**不含** OHLCV 原始價格；`LEGACY_17` 目前只剩儀表板的
即時預測路徑（`src/ml/predictor.py`）與部分舊版 UI 元件在使用。

## 7.4 為什麼要有 `CORE_16`：非平穩性

「非平穩」（Non-stationary）指一個數列會隨時間系統性地往某個方向
漂移（例如股價本身長期會受公司規模、通膨等因素影響而變大）。直接
拿這個數列當模型輸入，模型容易學到「這支股票的絕對價格區間」這種
與漲跌方向無關的虛假規律。`CORE_16` 把絕對價格（開高低收）換成比值型特徵（例如「今天
收盤價比 5 日均線高／低多少百分比」），讓數列的統計特性不隨時間系統性
漂移，模型比較不容易學到這種虛假規律。

## 7.5 NULL 語意學：一格空白有四種完全不同的意思

`daily_ml_features` 裡任何一格是空值（NULL）時，系統要求分辨這個
空值屬於以下哪一種成因：

| 成因代號 | 定義 |
|---|---|
| **W**（Warm-up，暖機期） | 這支股票或這個特徵剛開始追蹤，還沒累積到足夠的歷史天數（例如算 20 日均線，前 19 天結構上就是算不出來），**可以補值** |
| **F**（Source Failure，來源失敗） | 資料來源當天真的抓不到（例如爬蟲掛了），**必須保持空值、且訓練時要排除**——絕對不能補值，否則等於讓模型讀到一個「爬蟲掛掉」偽裝成的假訊號 |
| **U**（Undefined，數學上未定義） | 資料齊全、暖機期也過了，但公式本身在數學上算不出來（例如除數剛好是 0） |
| **S**（Suspect，可疑） | 資料有取到，但內部自相矛盾（例如留言的時間戳記出現倒退），需要額外檢查 |

`VERIFIED`：這套四分類法是在開發過程中，發現原本的兩分類（W／F）
不夠用後才擴充出來的。例如 `volume_ratio_5d`（成交量比）這個特徵在
「5 日均量剛好是 0」時會出現除以零，此成因既非暖機期不足（W），也
非資料來源失敗（F），而是**數學上這個公式本身就定義不出來**（U）。
這個發現使原本「NULL 只有兩種成因」的文件記載被判定為過度簡化，
需要補上第三種成因。

## 7.6 空日的「平均」不填中性值，但「計數」照樣補真值

情緒相關的 8 個特徵不是全部用同一套規則處理空值，而是依照「這一格
在數學上算不算得出一個真值」分開處理：

- **`sentiment_mean`（情緒均值）保持空值**：一天完全沒有文章時，「這天
  的情緒平均是多少」在數學上根本沒有答案，2026-09-08 之前的舊版本會
  補一個「0.5（中性）」——但那個 0.5 是編出來的，並不是「這天真的
  被觀察到中性討論」，已修正為保持空值，交由訓練時排除或讓模型自己
  的機制處理。`sentiment_3d_ma`／`sentiment_5d_ma`（3 日／5 日情緒
  均線）同理：用「窗口內至少有一天真的有資料」漸進計算，只有整個
  窗口都空的時候才保持空值。
- **`article_count`（文章數）、`bullishness_index`（看多指數）、
  `agreement_index`（一致性指數）補真值 0**：這幾個特徵在完全沒有
  文章的日子，公式本身就明確定義出 0（沒有文章＝文章數 0；看多指數
  公式在正負面篇數都是 0 時算出來就是 0）——這不是編出來的中性值，
  是公式在那個輸入下的真實計算結果。
- **`sentiment_lag_1`／`sentiment_lag_2`（前 1／2 日情緒滯後值）只在
  真正的「暖機期」（追蹤才剛開始、還沒有前幾天的資料）補 0.5**；如果
  前幾天資料存在、只是那幾天剛好也是空日，則保持空值，不會被那個
  0.5 蓋過去。

「情緒特徵一律不填中性值」的說法並不準確：僅有數學上算不出真值的
空日平均與滯後值不補中性值，計數類與指數類在空日有明確的真實答案，
仍照樣補真值。另外，僅邏輯迴歸（Logistic Regression）因無法處理
NaN 而被排除在使用完整特徵集之外，其餘模型皆保留 NaN，交由模型
自身機制處理，不因遷就特定模型而調整資料。

## 7.7 逐檔交易日曆

一個曾經真實發生的錯誤（登記在案的 RISK-027）：系統原本用「所有市場
交易日的聯集」當作統一的交易日曆，把台股文章的發文時間「往前捲」到
下一個交易日時，如果那天剛好是美股（NVDA）開盤但台股休市的日子，
台股文章就會被捲到一個台股根本不存在交易紀錄的日期上，合併資料時
不會報錯，但該篇文章的情緒訊號未被納入計算。發現的線索是「把 NVDA
從追蹤名單移除後，這個落差就消失了」。修法是
改成每支股票各自用自己所屬市場的交易日曆，而不是用一個全市場通用的
日曆。

## 7.8 留言特徵尚未真正啟用

三個留言衍生特徵在契約與資料庫結構裡都已經定義好，但截至報告撰寫時

# 第 8 章　時序驗證：如何證明沒有資料洩漏

## 8.1 前視偏誤：時序機器學習最容易犯的錯

前視偏誤（Look-ahead Bias）是時間序列機器學習中常見的錯誤：若訓練
過程中讓模型接觸到未來才會發生的資訊，測試階段的表現會失真地偏高，
應用於實際預測時則會失效。本專案的時序切分方式（8.2 節）用於系統性
防止此問題。

## 8.2 Purge、Gap、Embargo：三個防止洩漏的機制

把資料切成訓練集與測試集時，光是「按時間先後切開」還不夠，因為某些
資料列的「標籤結算日期」可能晚於它被歸類為訓練集的那個時間點。系統
用三個機制加強防護（`PURGED_WALK_FORWARD_SPEC.md`）：

- **Purge（清除）**：任何一筆訓練資料，如果它的標籤要等到測試期間才
  真正結算完成，就把這筆資料從訓練集裡拿掉——否則模型等於是在訓練時
  就偷看到了測試期間才會出現的資訊。
- **Gap（間隔）**：訓練集與測試集之間保留一段緩衝期，不使用。
- **Embargo（禁閉期）**：測試完成後，禁止把剛測試過的那段資料立刻拿
  回去訓練下一個時間窗——本專案目前設定 `embargo_days=0`（禁閉期為
  0 天），理由與驗證結果見 8.4 節。

所有時間單位都用「交易日」計算，不用日曆百分比，且系統核心斷言是：
**訓練集裡最晚的標籤結算日期，必須早於測試集裡最早的交易日**。這條
斷言由程式碼直接檢查（`assert_no_boundary_leakage()`），不是寫在文件
裡口頭要求。

## 8.3 Triple-Barrier 標籤：怎麼把「未來股價」變成一個分類問題

Triple-Barrier（三重障礙）是把「這筆交易之後會怎樣」轉換成三分類問題
的標籤方法：以隔天的開盤價為進場價，設定一個上障礙（達到就算獲利了結）
與一個下障礙（達到就算停損），並限制觀察期間（本專案設 5 個交易日）。
三種結果：

- `+1`：先觸及上障礙（獲利了結）
- `-1`：先觸及下障礙（停損）
- `0`：**Timeout**——觀察期間內兩個障礙皆未被觸及

同一天內兩個障礙同時被觸及時，系統的裁決是**標記為空值（NULL）**，
而不是用某種規則猜測「先觸及的是哪一個」——因為日內價格的實際順序
資料庫裡沒有記錄，猜測等於編造資訊。

同一個原則沒有被套用到二分類標籤上。`target_up_down` 的定義是「報酬
大於零算漲，其餘算跌」，因此報酬恰好等於零的平盤日被指定為「跌」。
以 Gate 3 使用的凍結面板計算（`VERIFIED`，139,400 筆有效列）：漲
47.68%、平盤 4.74%、跌 47.58%——**真實方向的多數其實是漲，「跌」之所以
成為多數類，完全來自平盤日被歸到這一邊**。若平盤改歸為漲，多數類會
翻面。

這與本節上一段對 Triple-Barrier 的處置（`DEC-018`：分不出方向即標
空值、禁止任意 tie-breaker）在原則上不一致。此不一致在本報告撰寫時
才被發現並登記，處置方向留待後續評估，未在本報告涵蓋的期間內修正。

## 8.4 洩漏診斷：拿真實結果檢驗 `embargo_days=0` 是否站得住腳

`embargo_days` 設為 0 不是憑感覺決定的，而是有一套獨立機制在檢查「這樣
設定會不會導致洩漏」。做法是把每個測試窗切成最靠近訓練／測試分界的
前 5 個交易日（邊界窗）與其餘天數（內部窗），比較兩者的 Macro-F1：
若訓練資料偷看到了未來，受影響的必是邊界窗——只有這幾天的標籤結算期
會與訓練資料重疊，因此邊界窗的表現理應系統性優於內部窗。`median_delta`
是各時間窗「邊界窗減內部窗」F1 差值的中位數，`frac_positive` 是邊界窗
表現較優的時間窗比例（僅在兩窗共有的類別上比較，避免 Timeout 類別
小樣本缺席造成假訊號）；兩個門檻須同時成立才判定有洩漏疑慮，避免只看
比例被「普遍偏一點」誤判、只看中位數被「少數偏很多」誤判。

`PREVIOUSLY VERIFIED`（基準 commit `dde7f4e`，2026-09-16，來源：
`UG_G3_SB3_report_target_*.json`）：
四個模型分別搭配「含情緒特徵」與「不含情緒特徵」兩種對照臂，但邏輯迴歸
不能吃空值（NaN），只跑「不含情緒」這一種臂，因此實際是 **7 組模型-特徵
組合**（而非 4×2=8 組）；這 7 組各自搭配 2 種切分模式（滾動／擴張窗口）
與 2 個預測目標，共 **28 組**洩漏診斷，**全部標記為「未發現洩漏」
（`flagged: False`）**。以其中 `logistic_regression__A`（漲跌方向、
滾動窗口）為例：`median_delta` 為 `-0.0387`，遠低於門檻
`LEAKAGE_MEDIAN_DELTA_THRESHOLD=0.05`；`frac_positive` 為 `0.326`，
遠低於門檻 `LEAKAGE_FRAC_POSITIVE_THRESHOLD=0.70`（兩個常數定義於
`src/ml/specialist_training.py`）。

`ENGINEERING JUDGMENT`：這兩個門檻是程式碼註解中明寫的工程判斷，不是
統計檢定，也非文獻或資料校準得出——依據是「多少比例的時間窗都偏向同一
方向、偏移量級是否值得注意」的實務判斷。已核准的是判準方法本身，數值
由實作者訂定，2026 年 9 月中旬寫入後沿用至今未再調整。

這項診斷附有已知會失敗的驗證：一個測試刻意不做 Purge、讓標籤依賴未來
日期，確認診斷真的會標記出來；另一個測試證明「任一時間窗偏正就標記」
這種更簡單的判準會給出不同結論，說明目前的判準不是隨手選定。同時明確
記載：此方法不保證能偵測所有可能的洩漏形式。

這代表目前的 `embargo_days=0` 設定，在邊界窗與內部窗的檢驗下沒有出現
系統性異常，而不是沒有檢查過就採用的預設值。

## 8.5 Holdout 邊界：把「唯一一次的真正測試」用程式碼鎖起來

除了滾動式的訓練／測試切分（用來反覆調整模型與方法），系統額外保留
一段**從頭到尾都不曾被任何模型訓練或選擇邏輯看過**的資料，稱為
Holdout（保留樣本），起始日期為 **2025-10-23**（`DEC-040`）。程式碼裡
有一個明確的檢查函式，任何嘗試讀取或訓練這段資料的動作都會直接丟出
例外阻擋，且橫跨這條邊界的資料折會**整段丟棄**，而不是把它切一半使用
——避免有人為了湊資料量而悄悄破壞這條邊界的完整性。這段資料只被讀取
**一次**，用來做最終的、樣本外的效果驗證（第 9.11 節）。

## 9.1 四個模型、43 個時間窗與兩種切分方式

系統訓練四類模型：邏輯迴歸（Logistic Regression）、隨機森林（Random

Triple-Barrier 三分類）分別測試滾動窗口與擴張窗口兩種切分模式。

以 Macro-F1 評估（各類別先計算 F1，即 Precision 與 Recall 的調和平均，
再對各類別等權平均、不依樣本數加權；實作見

0.4818，與不含情緒特徵的對照臂 A 差距不大。

這個 0.4899，高於「全猜多數類」的退化基準（中位數 0.3412，來源：

0.47536——與上方 43 個時間窗（不同資料切分）的 0.4899 屬不同來源，

分類能力的宣稱。**

```bash

rng=np.random.default_rng(0); n=17949; p=8603/n

for _ in range(20):

print('simulated', np.mean(r), np.std(r))"
```

## 9.3 模型堆疊：漲跌方向上退化，三分類目標上小幅改善

系統將四個模型輸出的預測機率作為新的輸入特徵，訓練一個 Meta-Learner，
測試 Stacking（堆疊）是否能提升預測效果。在漲跌方向預測任務中，
Stacking 模型的 Macro-F1 中位數為 **0.3812**，低於單一表現最好的
模型 LightGBM（**0.4654**）。加入 Meta-Learner 後，整體表現未提升，
反而下降。

`INFERENCE`：0.3812 已經接近同一份 JSON、同一 Meta-Eval 段的「全猜多數
類」退化基準（`comparison_meta_eval_macro_f1` → `"Majority Baseline":
0.3424`），代表 Meta-Learner 的輸出幾乎塌陷到單一類別——這比「表現未
提升」更具體地描述了退化的方式。
（來源：`doc/upgrade/gates/evidence/UG_G3_SB4_meta_learner_report_target_up_down.json`）

在 Triple-Barrier 三分類目標上，結果相反：Stacking
（Meta(A)-LogisticRegression）的 Macro-F1 為 **0.3175**，優於單一表現
最好的 Specialist（**0.3043**）。三分類的「按類別比例隨機猜」基準同樣
有解析解——K 個類別時恆為 **1/K**（與 §9.2 二分類的 0.500 是同一個
結論的 K=3 版本），本例 1/3≈0.3333，0.3175 仍略低於這個基準。

誠實的結論是：Stacking 相對單一模型有小幅改善，但 macro-F1 本身仍未
達隨機基準——它被保留在閘門路徑上的依據，不是 macro-F1，而是 Timeout
類別的 One-vs-Rest AUC 與閘門四項指標（見 §9.6、§9.8）。這也是
`src/ml/gating.py` 檔頭明訂「Meta(A)-LogisticRegression 為唯一 gating
來源」、以及 §9.12 把最終管線描述為
「Specialist→Stacking→Calibration→Gating 四層」的原因——這兩節說的是
同一件事，本節上一段的 up_down 結果不能被讀成「Stacking 全面沒有用」。
（來源：`doc/upgrade/gates/evidence/UG_G3_SB4_meta_learner_report_target_triple_barrier.json`
→ `comparison_meta_eval_macro_f1`）

## 9.4 機率校準未改善預測品質

機率校準（Calibration）的目的是讓模型輸出的機率更接近實際發生頻率
（例如模型判斷「70% 機率上漲」時，該群樣本實際上漲比例應接近
70%）。以 Brier Score（數值越低代表校準效果越好）衡量：校準前為
**0.49896**，使用 Isotonic Regression 校準後為 **0.49967**，數值
上升。本次校準未改善機率預測品質，系統診斷旗標標記為
`calibration_not_meaningful: true`。

`VERIFIED THIS SESSION`：這裡的 Brier Score 用的是
`brier_score_multiclass()`（`src/ml/calibration.py:372-386`），定義是
逐類別 one-hot 平方誤差加總，對二分類問題而言，數值是標準單一機率
Brier Score 定義的**兩倍**（程式碼 docstring 明載）。換算回標準 0–1
尺度：0.49896→0.2495、0.49967→0.2498。**0.25 正好是「模型完全沒學到
東西、每次都只輸出基期機率」的理論值**——兩個數字幾乎精準卡在這條線
上，這是 §9.5 AUC≈0.50 發現的第二重獨立佐證，不是校準這個技術本身
失敗，是「漲跌方向」這個目標從一開始就沒有可校準的訊號。

`INFERENCE`：這也解釋了「校準能讓 Brier Score 變差，卻不太可能讓
AUC 變差」這個看似矛盾的現象——AUC 只衡量排序，不衡量機率數值準確度，
單調轉換（Isotonic、Platt 皆為單調函式）理論上不改變排序，因此不改變
AUC。本專案把這個性質寫成一個會失敗的檢查：`assert_auc_preserved()`
（`src/ml/calibration.py:272-303`）斷言 Platt 校準前後 AUC 必須相等，
或在擬合出負斜率時精確鏡射為 `1 − AUC`（訊號趨近雜訊時，未正則化
擬合出負斜率是合法結果，正負號本身是雜訊），兩者皆不成立才判定排序
被破壞。known-FAIL 案例 `test_platt_broken_calibrator_changes_auc_raises`
（對調首尾兩點，製造真正的排序破壞）驗證過這個檢查真的擋得住異常。

## 9.5 關鍵診斷：底層模型缺乏有效的排序能力

前述 Macro-F1 結果顯示模型表現普通，需以 AUC（衡量模型能否將正例與
負例正確排序的指標，0.5 代表無排序能力，等同隨機判斷）進一步檢驗：

| 模型 | AUC（漲跌方向，Calib-Eval 段） |
|---|---|
| 邏輯迴歸 | 0.4923 |
| 隨機森林 | 0.5102 |
| LightGBM | 0.4997 |
| XGBoost | 0.5029 |

四個模型的 AUC 皆落在 **0.49～0.51** 之間，顯示無論採用哪一種模型，
對「明天會漲還是會跌」皆缺乏可辨識的排序能力。Macro-F1（0.4899，低於
隨機基準 0.500）與 AUC（0.49～0.51，隨機水準）兩項指標指向同一個結論，
並不衝突。兩者衡量的層面不同：Macro-F1 衡量在**單一固定門檻**下的硬

代表模型在兩個層面上都沒有可辨識的訊號。
（來源：`doc/upgrade/gates/evidence/UG_G3_SB5_calibration_report_target_up_down.json`）

`target_triple_barrier`（三分類：獲利了結／停損／Timeout）為三個

## 9.8 Calib-Eval 段的初步驗證結果

第一輪驗證使用 folds 30–32，尚未使用最終保留樣本。系統設定決策門檻
θ*：模型預測的 Timeout 機率高於此門檻時，判定該筆交易不建議進場。
選定門檻為 `θ*=0.06907`，結果如下：

門檻 θ* 的選定規則是「在覆蓋率≥80%、精準度提升≥4倍、召回率≥60%三項
判準同時成立的候選中，取召回率最高者」（`rule=
"max_recall_tiebreak_precision"`）。**覆蓋率剛好落在 80.00% 這個約束
邊界上，是規則生效的必然結果，不是獨立達成的觀測值**——相鄰格點
θ=0.065 的召回率更高（84.32%），但覆蓋率 79.13% 不合格而被排除。

- **覆蓋率 80.00%**——保留約八成交易機會，篩除其餘二成
- **精準度 19.56%**，相較於隨機基準精準度 4.71%，提升 **4.15 倍**
- **召回率 83.03%**——實際發生 Timeout 的交易中，約 83% 被正確篩出

## 9.9 決策門檻的取捨

決策門檻越低，判斷越嚴格：`P(timeout) > θ` 這個條件在低門檻下更容易
成立，會攔截更多交易，召回率較高，但可交易覆蓋率與精準度較低。門檻
提高後，只攔截模型最確定的 Timeout 樣本，精準度通常提升，召回率與
攔截量下降，可交易覆蓋率隨之上升。例如將門檻提高至 0.20，精準度提升
倍數增加至 8.70 倍，召回率降至 38.6%，覆蓋率則上升至 95.6%（僅 4.4%
的交易被攔截，多數應被篩除的交易反而未被攔下）。目前採用的門檻是在
保留交易機會與判斷準確度之間的折衷。

## 9.11 唯一一次正式驗證：Holdout 樣本外結果

第 9.8～9.10 節的數字來自反覆用於調整方法的資料段（folds 30–32）。
第 8.5 節定義的 Holdout 資料（folds 33–42，時間範圍 2025-10-23
之後）僅供最終驗證使用，讀取後不再回頭調整方法重測。

`VERIFIED`（`is_real_consumption: true`，來源：
`doc/upgrade/gates/evidence/UG_G3_SB7_holdout_report.json`）：

| 指標 | Calib-Eval（folds 30-32） | **Holdout（folds 33-42，唯一一次）** |
|---|---|---|
| 覆蓋率 | 80.00% | **92.52%** |
| 精準度 | 19.56% | **18.92%** |
| 召回率 | 83.03% | **80.28%** |
| 精準度提升倍數 | 4.15 倍 | **10.73 倍** |

三項判準（覆蓋率 ≥80%、精準度提升 ≥4 倍、召回率 ≥60%）在 Holdout
資料上皆成立。`INFERENCE`：精準度提升倍數由 4.15 倍上升至 10.73
倍，主要原因是 Holdout 期間 Timeout 基期比例（1.76%）低於
Calib-Eval 期間（4.71%），倍數計算以基期比例為分母，較低的基期會
放大倍數，此變化需要進一步驗證，不應直接解讀為模型在 Holdout 上
表現改善。

這三項判準是在觀察 Calib-Eval 曲線之後訂定的事後目標（`src/ml/
gating.py` 檔頭原文：「這三項判準是看過 Calib-eval 實測曲線之後訂的
事後目標，不宣稱在未來資料……上會穩定重現」），不是一個事前登記、
之後才拿真實資料檢驗的假設。Holdout 的意義在於它是**唯一一次**樣本外
檢驗——用完全沒被用來調整過任何方法的資料，確認同一組事後目標在新
資料上依然成立，而不是「通過一個獨立於資料之外的門檻」。

`INFERENCE`：本次樣本外驗證的對象是閘門的四項指標（覆蓋率／精準度／
召回率／提升倍數），不包含重新計算 Triple-Barrier 的 One-vs-Rest
AUC。§9.6 的 Timeout 類 AUC（0.90～0.91）屬 Calib-Eval 段量測值，
Holdout 報告未重新計算三分類 AUC，因此這個數字不具樣本外地位——引用
時應標明段別，不能與 Holdout 的驗證結果混為一談。

同一份 Holdout 報告顯示，漲跌方向預測在樣本外的結果與訓練期間一致：
四個模型的 AUC 落在 **0.505～0.523** 之間，仍缺乏排序能力。
`RISK-030`（漲跌方向無可偵測排序訊號）於此正式確立，樣本外結果未
推翻先前結論。

這 27 個關鍵字不是 27 檔股票——`tracking_keywords` 表把它們分成

從未對 458 檔股票逐一查詢過 PTT**。458 檔的價格資料來自完全獨立的
TWSE／TPEx 全市場報表（見 3.2 節），跟 PTT 擷取是兩套不相干的機制。

把「為什麼覆蓋率會低到 1%」拆開來看，是三層各自獨立的限制疊在

**第一層：時間（影響最大）。** 如 10.2 節所示，面板有 82.5% 的列

問題，加再多關鍵字也不會讓 2023 年的資料出現。

# 第 11 章　BI 視覺化層

## 11.1 單頁式儀表板

`app.py` 是一個單頁應用（沒有多頁籤結構），由上而下排列九個區塊：
側欄控制項（股票選擇、時間區間、資料來源狀態）→ AI 熱門詞徽章 →
題材概念雷達圖 → 三張關鍵指標卡片（股價／情緒／模型預測）→ 主圖表
（K 線圖疊加均線、成交量、情緒分數的雙 Y 軸圖）→ 策略報酬曲線圖與
特徵重要度圖 → 預測面板（含前三大影響因子）→ 模型競技排行榜 →
原始論壇文章表格。

## 11.2 四態資料模式貫穿全部載入器與渲染器

儀表板的每一個資料載入函式與渲染函式都會標記自己目前處於哪一種模式：

| 模式 | 意思 |
|---|---|
| `REAL` | 真實資料庫查詢結果 |
| `DEMO` | 示範用的模擬資料（畫面上會加浮水印標示） |
| `EMPTY` | 資料庫查詢正常，但真的沒有資料 |
| `ERROR` | 資料庫連線或查詢本身失敗 |

`ERROR` 與 `EMPTY` 這兩種狀態渲染出來的畫面是**完全沒有數字的空白
佔位符**，不會退回一組看似合理的模擬資料。此設計與第 3.4 節的三態
失敗語意為同一原則在不同層的實作：**資料庫查詢失敗不能被偽裝成
「沒有資料」，也不能被偽裝成「有資料」**。

## 11.3 已知缺口

`app.py` 側欄目前寫死一段過期的測試狀態字串（顯示某個舊的、遠低於
目前實際測試數量的數字），反映單一真相來源未被持續維護的問題，
留待後續小案修正。損益曲線圖呈現的是策略累積
報酬的示意圖，**沒有經過交易成本、滑價的計算，也沒有經過 Holdout
樣本外驗證**——這件事必須在圖說明文字裡明確標示，不能讓讀者誤以為
那是一個經過驗證的獲利宣稱。

# 第 12 章　工程治理與品質防線

## 12.1 雙人閘門流程

每一項工作變更遵循「Gate A（事前提案並取得授權）→ 執行 → Gate B
（事後證據審查）」的兩階段流程，且**通過一個 Gate 不會自動授權下一個
Gate**——每個 Small Batch（一個可獨立交付的最小工作單位）都要各自
取得授權。

## 12.2 證據標籤制度

所有量化描述都必須標註證據強度，例如 `VERIFIED`（本次或已記錄的實際
執行結果）、`INFERENCE`（由已知證據推導，但本身不是直接測量結果）、
`HYPOTHESIS`（尚未驗證的假設）。每個標籤都要附上「怎麼重新驗證這個
說法」的具體方式，而不是單純貼一個標籤了事。本報告全文遵循這套標籤
系統。

## 12.3 「為偵測而寫，不是為通過而寫」

早期一項跨文件檢查腳本寫成「在某份文件裡搜尋『fillna』這個關鍵字，
然後只在留言與推文欄位範圍內確認有沒有相關說明」，而**缺陷實際位於
情緒欄位，不在留言欄位**——此檢查在設計上不可能發現該缺陷，因為它
只檢查已知沒問題的範圍，因此持續顯示「通過」，但這代表檢查範圍設計
有誤，並非驗證完成。改用「從契約要求出發，逐一列出所有應受約束的
對象，反過來檢查文件有沒有涵蓋」的方法後，新的檢查立即失敗，抓出
三個先前被漏掉的問題。

## 12.4 每一項檢查都要能舉出一個「已知會失敗」的案例

宣稱一項自動化檢查有效之前，必須先示範一個確實會讓它失敗的具體
情境，並實際執行過一次。一個「從來沒有失敗過」的檢查，和一個
「不管輸入什麼都不會失敗」的檢查，從輸出結果無法區分——兩者皆只會
顯示「通過」。唯一能區分兩者的方法，是刻意觸發一次失敗，確認其
偵測能力。

## 12.5 Pre-commit Hook：把規則從「記得遵守」變成「不遵守就交不出去」

`.githooks/pre-commit` 有四道機械化檢查：跨文件契約驗證、空白字元／
換行符差異偵測、憑證外洩掃描（檔名與內容兩層）、staged 檔案清單列印。
每一道都設計成「訊號中斷時預設視為失敗」（fail closed）——曾經實測
證實：拿掉這個中斷保護機制後，一個本應被檢查擋下的變更，即使檢查
本身印出了「中止」的訊息，commit 依然會成功建立。一個在被中斷時
會悄悄放行的檢查，比完全沒有檢查更危險，因為它給人一種安全的錯覺。

## 12.6 TDD：先寫測試、看它失敗、再寫實作讓它通過

`git log` 裡可以直接看到成對出現的「紅測」與「綠測」commit（先提交
一個預期會失敗的測試，再提交讓它通過的實作）。`PREVIOUSLY VERIFIED`
（基準 commit `dde7f4e`，2026-09-16）：
commit 訊息裡明確標記「（RED）」與「（GREEN）」的配對共 **9 組**（可重跑
指令：`git log --format='%s' | grep -c '（GREEN）'`），另外還有 24 個
commit 標記「紅測」但沒有在訊息裡明確標出對應的綠測——這是整個開發
過程刻意採用的固定節奏，不是事後補上的測試，但不宜誇大成一個籠統的
「超過 17 組」。

## 12.7 測試環境降級的誠實揭露

在缺少 `scikit-learn`／`lightgbm`／`xgboost` 等套件的降級環境（例如
開發者本機 Windows 環境）裡，`lightgbm` 與 `xgboost` 這兩個模型會
對映到**同一個**簡化替代實作類別——代表在降級環境下，所謂「四模型
競技」實際上只有兩種真正不同的實作在跑。這是主動記錄下來的已知
限制，也是為什麼本報告所有模型結果都明確標示「在容器內產出」，而
