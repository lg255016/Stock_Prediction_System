### 1.2 【阻擋級】DEC-024 的一致性約束，與契約 §4.3 的寫入模型直接衝突

**這是本次靜態核對最重要的發現，且與 Dcard 端點是否可用完全無關——
即使可用性驗證 PASS，不先解決這個衝突就無法寫入任何一筆 Dcard 文章。**

| 事實 | 來源 | 證據標籤 |
|------|------|---------|
| `MULTI_SOURCE_DATA_CONTRACT.md` §4.3 規定 Dcard 的 `commentCount` → `total_comments`，**於文章初次寫入時就帶入** | 契約原文欄位映射表 | `VERIFIED THIS SESSION` |
| `chk_comments_scraped_at_consistency` 要求 `comments_scraped_at` 與 `total_comments` **同時為 NULL 或同時非 NULL** | `database/migrations/004_comment_scrape_timestamp.sql`（DEC-024） | `VERIFIED THIS SESSION` |
| `DBWriter.ARTICLE_COLUMNS`（INSERT 路徑）**不含** `comments_scraped_at` | `src/loaders/db_writer.py:132-137` | `VERIFIED THIS SESSION` |

**推導結果**：Dcard 若照契約 §4.3 在 INSERT 時帶入 `total_comments`，該列會是
`total_comments` 非 NULL、`comments_scraped_at` NULL → **違反 CHECK 約束，整批 INSERT 失敗**。
（標籤：`INFERENCE`——由上述三項已驗證事實推導，尚未對真實 DB 執行以觀察 `CheckViolation`；
若本 SB 獲准，E2E 會實際驗證此推導。）

**PTT 為何沒踩到**：PTT 走的是「INSERT 時 `total_comments` 為 NULL → 之後由
`update_comment_counts()` 同時寫入計數與 `comments_scraped_at`」的 backfill 模型
（DEC-024 write-once），INSERT 當下兩欄皆 NULL，滿足約束。

**根因**：DEC-024 的設計前提是「留言計數與其擷取時點必須成對」，這是為 PTT 的
backfill 模型量身訂做的；而 Dcard 契約假設的是「文章與留言數一次取得」的模型。
兩個都是已核准的產物，但**從未一起檢視過**。處置見 §6 決策點 1。

### 1.3 `engagement_metric` 的跨來源語意分歧

| 來源 | `engagement_metric` 實際含意 | 值域 |
|------|---------------------------|------|
| PTT（現行） | 列表頁推文徽章經 `_parse_push_count()` 轉換（「爆」→`100`、「X…」→`-10`） | **有正負號的淨值** |
| Dcard（契約 §4.3） | `likeCount`（愛心數） | **恆 ≥ 0 的計數** |

同一欄位承載兩種不可比較的量。這與 `UG-G2-SB3` 登記的 `push_count` 雙語意陷阱同型，
但這次是**跨來源**而非跨層。

**兩者連數學性質都不同（PO 於 Gate A 審查時補充）**：PTT 的是**帶符號的淨值**，
Dcard 的是**非負計數**。後果具體如下——一篇被噓爆的 PTT 文章（`-10`）在排序時會排在
一篇零讚的 Dcard 文章（`0`）**後面**，看起來像「比較不受關注」，
實際是「非常受關注但一面倒被罵」。**排序結果會與事實相反。**

**且下游確實有消費者——本提案初稿誤判此點，已更正**（`VERIFIED THIS SESSION`）：

| 位置 | 行為 |
|------|------|
| `src/ui/data_loader.py:410` | SQL 中 `engagement_metric AS push_count`——**直接改名為 `push_count`** |
| `src/ui/components.py:310` | 以 `push_count` 欄排序輿情明細表 |
| `src/ui/components.py:318` | 該欄在 UI 顯示為 **「推噓數」** |

也就是說：Dcard 文章一旦寫入，**其 `likeCount`（愛心數）會在 UI 上被標示為「推噓數」，
並與 PTT 的推噓值混在同一欄排序**。這不是未來的假設風險，是既有 UI 路徑會立即發生的
**呈現層失真**——而且它不會報錯，只會顯示一個看起來正常但語意錯誤的數字。

初稿寫「僅命中寫入路徑」是因為我只掃了寫入端就下結論，沒有把 `src/ui/` 的讀取路徑
看完。此類「grep 了但沒看完就下結論」正是 `CLAUDE.md` §9A.1 警告的同型錯誤，
在此如實記錄。

嚴重度因此**由「非阻擋級」上修為「`PASS` 情境下的阻擋級」**——若可用性驗證 PASS
而要實際寫入 Dcard 資料，此項須與 §1.2 一併處置。見 §6 決策點 3。

### 1.7 【阻擋級，PO 於 Gate A 審查時發現】`fillna(0)` 會讓 Dcard 製造偽造的「最大分歧」訊號

`src/transform/feature_aggregator.py:554-555`（`UG-G2-SB4` 寫入）：

```python
for col in ['push_count', 'boo_count']:
    df[col] = pd.to_numeric(df.get(col), errors='coerce').fillna(0)
```

Dcard **沒有推／噓的概念**，其 `push_count`／`boo_count` 必然是 `NULL`。
經這兩行補成 `0` 後，`push_ratio = (0-0)/(0+0+1) = 0`，
於是 `comment_polarization = 1 - 0² = 1.0`——**「最大分歧」**。

**本次獨立重現（`VERIFIED THIS SESSION`，未修改任何程式碼，僅觀察現況行為）**：

```
輸入：連續三日各一篇「Dcard 型」文章（total_comments=50/60/70，push/boo 皆 None）

trade_date  comment_volume_ratio  comment_polarization  net_push_momentum
2026-08-24                   NaN                   1.0                NaN
2026-08-25              1.176471                   1.0                0.0
2026-08-26              1.250000                   1.0                0.0
```

**比單日觀察更嚴重**：
- `comment_polarization` **每一天都是 1.0**——不是偶發，是恆定的偽造極端值。
- `net_push_momentum` 自第二日起**恆為 0.0**——偽造出「情緒方向毫無變化」。
- `comment_volume_ratio` **正確計算**（1.176／1.25）——因為數量本來就不需要方向。

最後一列正是關鍵證據：**同一批資料裡，只需要數量的特徵是對的，需要方向的特徵是假的。**

**這正是 `DB_MIGRATION_PLAN.md` §4.3 用一整段警告在防的那個偽造訊號**，
只是這次不是從 `DEFAULT 0` 那道門進來，而是從**跨來源**這道門。
`fillna(0)` 在 `UG-G2-SB4` 當時是合理的（只有 PTT 一個來源，NULL 確實代表「零則推文」）；
**一旦引入沒有推噓概念的來源，它就變成偽造訊號的產生器**。
與 §1.3 同樣不會報錯，只會安靜產出看似合理的極端值。

#### 1.7.1 【第二輪查證】只拿掉 `fillna(0)` **修不好**這個 bug（PO 指出，本次實測確認）

PO 於第二輪審查指出兩件初稿沒查的事。本次於 dev container 實測
（pandas 3.0.5 / numpy 2.5.2 / Python 3.14.6，`VERIFIED THIS SESSION`）：

| 觀察 | 結果 | 含意 |
|------|------|------|
| 全 NaN 群組 `.agg(push_sum=('push_count', 'sum'))` | **`0.0`** | **拿掉 `fillna(0)` 之後，NaN 仍在聚合層被變回 `0`**——偽造訊號原封不動 |
| 同一群組 `sum(min_count=1)` | `NaN` | 必須**明確指定 `min_count=1`**，NULL 才會傳播 |
| `push_ratio(0, 0)` | `0.0` → `polarization = 1.0` | 偽造的最大分歧 |
| `push_ratio(NaN, NaN)` | `NaN` → `polarization = NaN` | 正確行為 |
| 零推文 PTT 文章（整數 `0`） | 聚合後 `0`，`notna = True`（`min_count=1` 下亦同） | **真正零推文不會被誤判為 NULL** |

**第一列是本次最重要的發現**：`fillna(0)` 只是**第一道**把 NULL 壓成 `0` 的地方，
`groupby().agg('sum')` 是**第二道**，而且它不在任何人的視線裡——
把 `fillna(0)` 那兩行刪掉，測試仍然會 FAIL，且看起來像「修了但沒效」。

**PO 提出的反向風險經實測不成立**：`ptt_scraper.py:137-153` 三個計數器以整數 `0`
初始化並累加，零推文文章寫入 DB 的是 `0` 而非 `NULL`（上表末列）。
`0`（有方向，值為零）與 `NULL`（無方向的概念）在 DB 層**本來就可區分**，
**唯一會把兩者壓平的是聚合層**。這正是決策點 5 的修法必須同時處理
`fillna(0)` 與 `min_count` **兩處**的原因——只改一處會產生「已修復」的錯覺。

### 1.8 【新增】契約 §4 自身矛盾：端點不支援關鍵字搜尋，`fetch_keyword` 無來源

**PO 於 Gate A 審查時指出，本提案初稿只核對了欄位存在性，沒有核對「抓取模型」是否可行。**

| 契約位置 | 內容 | 矛盾 |
|---------|------|------|
| §4.2 | `GET /service/api/v2/forums/stock/posts?popular=true&limit=30&before={cursor}` | 這是**股票板熱門文章列表**，**無任何關鍵字參數** |

契約沒有規定替代作法（例如抓回熱門列表後在本地以標題比對關鍵字）。
這是**抓取模型層級**的缺口，不是欄位映射的細節，須於實作前釐清。見 §6 決策點 6。

### 1.12 【第二輪查證．PO 指出】混合來源日會噴出**純由來源組成造成**的尖峰

本提案第一輪在決策點 5 寫下「**數量可以跨來源相加**」。PO 指出該結論
**只在來源組成穩定時成立**，而 §1.7 的重現三天都是純 Dcard，測不到組成改變的斷點。

**本次實測（dev container，pandas 3.0.5，`VERIFIED THIS SESSION`）**：
前 5 日純 PTT（每日 `total_comments = 20`），第 6 日 PTT 20 **＋ Dcard 200**；
對照組第 6 日只有 PTT 20。

| trade_date | 純 PTT（對照組） | 混合來源 |
|-----------|----------------|---------|
| 08-18 ~ 08-21 | 0.952381 | 0.952381 |
| **08-24** | **0.952381** | **10.476190** |

**同一批 PTT 資料、同樣的關注度，只因為多了一個來源，比值就跳了 11 倍。**
分子含兩來源，分母的 `t-5..t-1` rolling 基準卻全是純 PTT
（`feature_aggregator.py:582-587` 的 `shift(1).rolling(5)` 配上 `:557-560` 的 `total_sum`）。
`comment_volume_ratio` 的定義是「今日相對於自己近 5 日的相對熱度」；
基準期與當期的**來源組成不同**時，它量到的不是關注度變化，是**來源上線事件**。

**同一次實測另發現方向與數量的不對稱**（初稿與 PO 均未提及）：
混合日的 `push_sum` 只由 PTT 的 20 則貢獻（Dcard 為 NaN，`min_count=1` 下仍被 sum 略過），
`push_ratio = 0.615`，但同一列的 `total_sum = 220`——
**方向特徵描述的是 20 則留言，數量特徵描述的是 220 則**。兩者並列於同一列，
隱含「這是同一群人的意見」，實際不是。

**結論修正**：「數量可以跨來源相加」**限縮為**——

## 3. 【核心】可用性判準——**執行任何驗證之前定死，須經 PO 核准**

> **不得因為結果不理想而調整判準後重跑。** 若判準本身有缺陷需要修改，

### 3.1 執行參數（固定，不得於執行時調整）

| 項目 | 值 |
|------|-----|
| 逾時 | 每次請求 15 秒 |
| 重試 | 最多 3 次，指數退避 2s → 4s → 8s（沿用 `ptt_scraper` 既有慣例） |
| 請求間隔 | 1.5–3.0 秒隨機延遲（契約 §4.4） |
| **總請求上限** | **整個驗證最多 3 次 GET**（端點清單見 §3.2），**不分頁、不抓取實際資料** |
| 列表端點參數 | A1 以 **`?popular=true&limit=30`** 發出，**對齊契約 §4.2 的正式端點參數**（第三輪裁示，見 §3.2.2）；**A3／A4／A5／A6 全部沿用同一個回應**，不另發請求 |
| User-Agent | 與 `ptt_scraper` 相同的瀏覽器 UA |
| 執行環境 | dev container |

**總請求上限的用意**：這是可用性**驗證**，不是資料擷取。上限使它不會在判定 FAIL 之前
先變成一次小規模爬取。

> **【第二輪補正】「重試 3 次」與「總請求上限 3 次」原本互相矛盾**——
> 初稿同時寫了這兩項，但沒說重試算不算進上限。若算，第一個請求重試兩次就用完預算；
> 若不算，上限形同虛設（3 × 3 = 最多 9 次 GET，而文件寫的是 3 次）。
> **釐清後的定義**：上限 3 次指的是**邏輯請求（端點）數**；
> 重試是同一個邏輯請求的重複嘗試，另設 **HTTP 嘗試上限 9 次**，
> **兩個數字都會被記錄在證據裡**（`budget` 欄）。
> 重試**只在傳輸層錯誤、429 與 5xx 時發生**——其餘 4xx 代表端點已明確回答，
> 重試不會改變答案，只會多打對方伺服器。
> 腳本以 `RequestBudget` 類別實作，超限**拋 `RuntimeError` 中止驗證**，
> 而不是靠註解提醒（`dcard_availability_check.py` 的 `RequestBudget` docstring 說明了原因）。

### 3.2 五項判準（A1–A5），全部 PASS 才算整體 PASS

| # | 判準 | 請求 | PASS 條件（機械可判定） | FAIL 條件 |
|---|------|------|----------------------|----------|
| **A1** | 端點連通性 | `GET /service/api/v2/forums/stock/posts?limit=30` | HTTP status **== 200** | 非 200（含 403／429 重試耗盡）、連線失敗、逾時 |
| **A2** | 匿名性**自我檢查** | 同 A1 之**實際送出標頭**（`resp.request.headers`） | 實際送出的標頭不含 `Cookie`／`Authorization`／`Proxy-Authorization` | 實際送出了上述任一標頭 |
| **A3** | 回應可解析且非空 | 同 A1 之回應 | `json.loads()` 成功，且頂層為 list、`len >= 1` | 解析失敗／非 list／空 list |
| **A4** | 欄位契約相符 | 同 A1 之回應第一個元素 | 契約 §4.3 的五個必要欄位**全部存在**且型別可用：`id`（可轉 `str`）、`title`（`str`）、`createdAt`（可 `pd.to_datetime` 解析）、`likeCount`（`int`）、`commentCount`（`int`） | 任一欄缺失或型別不符 |
| **A5** | 單篇與留言端點存在 | `GET /service/api/v2/posts/{id}`、`GET /service/api/v2/posts/{id}/comments?limit=1`（`id` 取自 A3 第一篇） | 兩者皆 HTTP **200** 且回應為合法 JSON | 任一非 200 或非合法 JSON |

**整體判定**（第四輪複查新增第三態）：

| 順序 | 條件 | 整體 |
|------|------|------|
| 1 | 任一判準 `NOT EXECUTED` **且 `blocked_by` 為 `None`** | **`INCONCLUSIVE`** |
| 2 | A1–A5 **全部 `PASS`** | `PASS` |
| 3 | 其餘 | `FAIL` |

**順序有意義：先看儀器有沒有壞，再看端點答得對不對。**

仍**不設**「部分通過」「有條件通過」等中間狀態——中間狀態正是預設立場最容易滲入的地方。

#### 3.2.2a `INCONCLUSIVE` 為何不是「中間狀態」

`INCONCLUSIVE` **不是 `PASS` 與 `FAIL` 之間的中間值**。
§3 禁的是「部分通過／有條件通過」那種**把壞結果洗成好結果**的中間值；
`INCONCLUSIVE` 說的是**「這次執行根本沒產出可用的觀察」**——它比 `FAIL` **更嚴格**，
不是更寬鬆。**它同樣不得被讀成「可用」。**

觸發條件是**機械的**，且資料裡本來就有：
`verdict == NOT EXECUTED` 而 `blocked_by is None`，
意思是**沒有任何上游判準擋住它，它卻仍然沒能執行**——
那只有一種可能：**儀器（本腳本）自己沒產出證據。**

目前只有兩個來源，**兩個都是我們自己的問題**：

| 來源 | 情境 |
|------|------|
| A2 | `sent_headers` 缺席——腳本沒記錄實際送出的標頭 |
| A1 | 列表請求根本沒發出（`attempted` 為 `False`） |

這是 §3.2.1 已經建立、但原本只停在「單項」層級的區分，現在抬到「整體」層級：

| 情境 | 是誰的問題 | 整體 |
|------|-----------|------|
| 端點答錯（非 200、格式變了、欄位缺了） | 端點 | `FAIL` |
| 上游判準擋住、沒機會跑 | 端點（根因仍在端點） | `FAIL` |
| **儀器沒產出證據，端點本身沒答錯** | **我們** | **`INCONCLUSIVE`** |

**邊界案例（本提案補充，複查未指定）**：若儀器故障與端點答錯**同時發生**，
依上表順序 `INCONCLUSIVE` **勝出**。

**理由（第四輪複查補強，原稿的理由偏弱）**：
原稿寫的是「儀器壞掉時端點的答案不論對錯都沒有資格進永久紀錄」，
這會被質疑「**A2 壞掉關 A4 什麼事**」。真正的理由更具體：

> **`sent_headers` 缺席代表我們不知道那個 200 是不是匿名取得的。**
> 若它其實帶了憑據，A3／A4／A5 觀察到的就是**認證後的回應**，未必等於匿名回應——
> **所有下游觀察的代表性都因此無從確認。**

所以不是「儀器壞了所以不信」，而是「**A2 這一項壞掉，恰好會使其餘觀察的代表性無從確認**」。
A2 在這五項裡的位置是特殊的：它界定的是**其他四項觀察到的東西是在什麼身分下取得的**。

**逐項 verdict 仍完整保留在證據裡**，重跑後會得到乾淨的判定。
已由 `test_instrument_failure_wins_over_genuine_failure` 釘住。

#### 3.2.0 A2 的性質——**它不是對端點的探測**（第三輪複查指出並修正）

初稿把 A2 寫成「免登入可存取」，讀起來像在探測端點的認證需求。**那個描述不成立**：
要真的證明「免登入可存取」，必須**帶認證與不帶認證各打一次做對照**，
而那超出本 SB 的授權與 §3.1 的請求上限。單方向的一次請求，
在原理上無法把「端點不需要認證」與「我們剛好沒帶認證」分開。

**A2 的真實性質是：對我們自己執行紀律的自我檢查**——
確認這次 A1 的 200 **不是靠環境裡某個認證憑據換來的**。
它不在「五項判準」裡充人數，它防的是一種特定的假 PASS：
**在有憑據的環境下驗到 200，然後宣告「公開可用」。**

##### 修正前的 A2 在正式執行下結構上不可能失敗

複查指出：`fetch()` 原本只記錄我們**打算**送出的本地字典
（`{"User-Agent": ..., "Accept": ...}`），而 A2 判的正是那個字典。
於是正式執行時 `auth_like` 恆為空，**A2 恆等於 A1**。

更嚴重的是它**檢查的物件本身就錯了**：容器內 `requests` 為 **2.34.2**，
其 `Session.prepare_request()` 會呼叫 `get_netrc_auth()`——
`~/.netrc`（或 `NETRC` 環境變數指向的檔案）存在時會**自動補上 `Authorization`**；
env proxy 亦可能補 `Proxy-Authorization`。**這些都不會出現在那個本地字典裡。**
也就是說：**真的送出了認證，A2 仍會回報「未送出任何認證標頭」。**

**修正**：`fetch()` 改為同時記錄 `intended_headers`（打算送的）與
**`sent_headers`（`resp.request.headers`，實際送出的）**，A2 改判後者。
`sent_headers` 缺席時記為 `NOT EXECUTED`（沒有證據不等於通過），不記 `PASS`。

**同一次真實請求的前後對照**（本機臨時 HTTP server，`VERIFIED THIS SESSION`，
未對 Dcard 發出任何請求）：

| | 結果 |
|---|---|
| HTTP status | 200 |
| `intended_headers` 含 `Authorization`？ | **否** |
| `sent_headers` 含 `Authorization`？ | **是** |
| **修正前** A2（判 `intended_headers`） | **`PASS`** ← 認證真的送出去了，卻回報通過 |
| **修正後** A2（判 `sent_headers`） | **`FAIL`**：實際送出了認證標頭 `['Authorization']` |

> 這與 GOV-04「檢查 2 的假通過」同型：**案例會 FAIL，但它證明的不是這道檢查
> 在正式執行時擋得住任何東西。** 分辨兩者的唯一方式，是讓真實路徑失敗一次。

#### 3.2.1 `NOT EXECUTED` 規則（PO 於 Gate A 審查時補上的缺口）

A4 需要 A3 的第一個元素、A5 需要該元素的 `id`。因此**若 A3 FAIL（例如頂層不是 list
或為空），A4 與 A5 在技術上根本無法執行**。初稿只寫「任一 FAIL → FAIL」，
未規定此情況下 A4／A5 該記成什麼。

**規則**：**無法執行的判準記為 `NOT EXECUTED`，並註明被哪一項阻斷，不得記為 `FAIL`。**

理由：`FAIL` 表示「跑了、不通過」，`NOT EXECUTED` 表示「沒機會跑」——
把後者記成前者會讓證據誤導未來重新評估的人，
讓他以為欄位契約也已被實測否定（實際上完全沒測到）。
**整體判定仍為 `FAIL`**（因為 A3 FAIL），但證據必須誠實區分這兩種狀態。

| 阻斷來源 | 連帶無法執行 |
|---------|-------------|
| A1 FAIL（連不上） | A2／A3／A4／A5 全部 `NOT EXECUTED` |
| A3 FAIL（回應無法解析／為空） | A4／A5 `NOT EXECUTED` |
| A4 FAIL（欄位缺失） | A5 視 `id` 是否存在而定：`id` 缺失 → `NOT EXECUTED`；`id` 存在但其他欄缺失 → A5 仍可執行 |

#### 3.2.2 A6：關鍵字覆蓋率量測——**量測項，不是判準項**（PO 第二輪指定）

**A6 不設 PASS 門檻，不參與整體判定。**
PO 的理由：**單一時點 30 篇撐不起數字門檻，設一個只會是假精確。**
它的用途是把決策點 6 的「覆蓋率可能極低」從猜測變成一個**有數字的觀察**。

| 項目 | 內容 |
|------|------|
| 資料來源 | **A1 的同一個回應**（`limit=30`），**不額外發出任何請求** |
| 量測內容 | 30 篇標題中命中 `is_active = TRUE` 追蹤關鍵字的**篇數**、以及**命中了哪些詞** |
| 必記背景 | 當時關鍵字清單的**全文與筆數** |
| 關鍵字來源 | **事前快照進證據檔**；**驗證腳本不連 DB**（PO 指定） |
| 判定 | 無。記錄為 `MEASURED`，不影響 A1–A5 的整體判定 |

**`limit` 由 1 改為 30 的性質**：契約 §4.5 原文寫 `limit=1`，§4.2 的正式端點本來就用
`limit=30`。改的是**單次請求要回幾筆**，不是**要發幾次請求**——
**總請求上限維持 3 次**。此變更構成對契約 §4.5 的偏離，登記見 §13（偏離二 (ii)）。

##### A6 的母體——**已對齊**（第三輪裁示：加上 `popular=true`）

第二輪時 A1 不帶 `popular=true`，量到的是「**最新** 30 篇」，
而決策點 6 方案 (a) 實際會抓的是「**熱門** 30 篇」——**不同母體**。
本提案當時只作揭露並請 PO 裁示。

**裁示：照改。** 理由即本提案自己寫的那句——
**量錯母體的覆蓋率數字，其誤導性大於沒有數字。**

A1 現為 `?popular=true&limit=30`，**A6 的母體與方案 (a) 實際會抓的母體一致**。
請求數不變（仍是同一次 GET）。

> **這個改動的性質**（複查指出，本提案原本寫錯了）：加上 `popular=true` 之後，
> A1 是**更貼近契約 §4.2 的正式端點**，**不是又偏離一次**。
> §13 偏離二 (ii) 的措辭已據此改寫。

##### A6 的比對規則（第三輪複查指出，須於證據中載明）

A6 以 **子字串比對**（`kw in title`）判定命中，**不做斷詞**。
容器內實測：關鍵字 `2330` 會命中標題 `12330` 與 `23300`。

量測當時 `tracking_keywords` 的 `is_active` 詞彙**全為中文詞**
（`schema.sql:128-140`），無數字型關鍵字，**實際風險低，本 SB 不改**。
但 **AI 熱門詞探索會動態加詞**，日後若出現數字型關鍵字，此數字會偏高。
腳本已把 `match_rule` 與 `match_rule_caveat` 寫進證據輸出，
使這個限制隨數字一起被讀到，而不是只存在於本提案裡。

### 3.3 必須記錄的原始證據（無論 PASS 或 FAIL）

- 每個請求的：完整 URL、HTTP status code、回應時間、重試次數
- A3／A4 的回應：頂層型別、`len`、第一個元素的**完整 key 清單**（不只是缺哪一個）
  ——PO 特別指出此項的價值：它讓「**端點還在但契約過期**」與「**端點消失**」
  這兩種 FAIL 能被區分，前者可修（改欄位映射）、後者不可修（來源沒了）。
- FAIL 時：回應 body 前 500 字元（若為 HTML 錯誤頁，記錄其 `<title>`）
- **每項判準的三態結果**：`PASS`／`FAIL`／`NOT EXECUTED`（後者須註明阻斷來源，見 §3.2.1）
- 執行時間戳（UTC + 本地）與執行環境

### 3.4 明確不納入本次判準的事項

- **資料品質**（文章是否與股票相關、雜訊比例）——那是可用性成立**之後**才有意義的問題。
- **長期穩定性**——單次驗證無法證明；即使 PASS，RISK-003 也不應降為「已解決」。
- **使用條款合規性**——見 §6 決策點 2，不由本判準裁定。
- **理財板（`money`）**——契約 §4.1 的目標板塊有兩個，本判準只驗 `stock`。
  `PASS` 只能讀成「**股票板**可用」（§1.9）。
- **A6 的關鍵字覆蓋率**——量測項，**不參與判定**（§3.2.2）。

## 4. 【核心】`FAIL` 的處置路徑——與 `PASS` 同等具體

### 4.1 若整體判定為 `FAIL`

| # | 動作 | 具體內容 |

### 決策點 5【新增．阻擋級】：來源能力（Source Capability）的抽象——§1.7 的正確修法

**PO 於 Gate A 審查時指出：真正的問題不是「補 0」，是系統缺少「來源能力」的概念。**

PTT 與 Dcard 在留言上的**唯一實質差別**：

| | PTT | Dcard |
|---|-----|-------|
| 一則留言 | 推／噓／→ 三種標記 | 就是一則留言，**無分類** |
| 能得到 | 數量 **＋ 方向** | **只有數量** |

`push_ratio` 不是本專案設計出來的指標——它之所以存在，純粹是因為 **PTT 的資料結構
本來就提供方向**。Dcard 要有方向，得對**每則留言文字**做 NLP，
而本系統只對**標題**做 NLP（`nlp_processor`），結構上做不到。

因此三個留言特徵對來源的要求並不相同：

| 特徵 | 需要什麼 | PTT | Dcard |
|------|---------|-----|-------|
| `comment_volume_ratio` | 只要**數量** | ✅ | ✅ **可跨來源相加** |
| `comment_polarization` | 需要**方向** | ✅ | ❌ **結構上不可能** |
| `net_push_momentum` | 需要**方向** | ✅ | ❌ **結構上不可能** |

**數量可以跨來源相加，方向不行。** §1.7 的實測正好證實這點——
同一批 Dcard 資料裡，`comment_volume_ratio` 算對了，另兩個是假的。

**正確的抽象**：讓每個來源**明確宣告它能提供什麼**——所有來源提供「留言數量」，
只有部分來源提供「留言方向」。需要方向的特徵遇到不提供方向的來源時
**保持 `NULL`**——**不是補 0，是誠實地「這個來源答不出這題」**。

這與本專案已確立的原則完全一致（`DEFAULT 0` 禁令、`source_status` 四態、
`label_reason` 的「尚未計算」語意），只是尚未套用到**跨來源**這一層。
且 **Threads（RISK-004）將來同樣沒有推噓——這不是 Dcard 的個案**，
是每一個新來源都會遇到的結構性問題。

#### 決策點 5 裁決（PO，2026-08-28 第二輪）：**明確的來源能力宣告，本 SB 完成，只做 comment direction 這一項能力**

**不採 `push_count IS NULL` 隱含判定。** PO 的理由：
`FEATURE_REGISTRY.md:388-391` 已把 `NULL` 定義為「**留言尚未解析**」，
再讓它兼任「**這個來源沒有方向的概念**」，就是**用同一個值裝兩種語意**——
而那正是 §1.3 與 `UG-G2-SB3` `push_count` 雙語意陷阱的成因。
本專案已經因為同一個病吃過兩次虧，不會用第三次。

**PO 補上的論證（比本提案原本寫的更強）**：
契約 §4.3 的欄位映射表**只有 8 列**，`push_count`／`boo_count`／`neutral_count`
**三欄完全不在裡面**。也就是說——

> **「Dcard 沒有方向」是 Gate 0 契約本來就已經隱含承認的事。
> 決策點 5 不是發明新概念，是把契約已經默認的事，變成程式碼看得懂的宣告。**

**範圍限定**：只宣告 **comment direction（留言方向）** 這一項能力。
**不建立一般化的來源能力協商層**——宣告表可擴充即可（PO 機械要求 3）。

##### 落地形式（本提案提出，供複查）

```python

# 來源能力宣告表（決策點 5，PO 2026-08-28）
# 宣告的是「這個來源在結構上能提供什麼」，不是「這次有沒有抓到」。
```

3. 聚合改用 **`min_count=1`**——否則全 NaN 群組仍會 sum 成 `0.0`（§1.7.1 實測）。
4. `has_comments` 拆為 `has_volume`（`total_sum.notna()`）與

##### 【本輪新增】`fetch_keyword` 是同一個病的**第三個現場**（PO 指出）

初稿在 (a) 寫「與 PTT 語意最接近」。**該句已刪除**，因為它掩蓋了真正的差異：

| 來源 | `fetch_keyword` 的真實意義 | 抽樣過程 |
|------|-------------------------|---------|
| PTT | **因為搜尋了這個詞，所以抓到這篇** | **關鍵字驅動抽樣** |
| Dcard（方案 a） | **因為熱門所以被抓到，事後發現標題裡有這個詞** | **熱門度條件抽樣** |

兩者混進同一欄之後，下游 `direct_count` 那一族
（`direct_count`／`direct_sentiment_mean`／`direct_pos_count`／`direct_neg_count`，
`feature_aggregator.py:269-273`）就成了**兩種抽樣過程的混合物**——
「這檔股票今天有 8 篇文章」不再是一個定義明確的量。

這與 §1.3（`engagement_metric` 一欄兩義）、§1.7／§1.12（`NULL` 一值兩義、
數量與方向不同母體）**是同一個病的第三個現場**：
**把兩種來歷不同的東西塞進同一個欄位，然後在下游假裝它們可比較。**

**直接後果（已寫入 §4.2.1）**：即使 A1–A5 全部 `PASS`，
**SB5 的 `PASS` 也不等於「Dcard 可以開始貢獻特徵」**。
「Dcard 抓回來的東西該不該與 PTT 混算」是一個**尚未回答**的問題，
本 SB 的交付物包含「把這個問題問清楚並附上 A6 的數字」，**不包含回答它**。

### 17.2 【關鍵】FAIL 的性質：**Cloudflare 邊緣攔截，不是「端點消失」**

§3.3 要求記錄的原始證據，正是為了讓這個區分成立：

| 證據 | 值 |
|------|-----|
| HTTP status | **403** |
| `Content-Type` | `text/html; charset=UTF-8`（**不是 JSON**） |
| HTML `<title>` | **`Attention Required! | Cloudflare`** |
| `Server` | **`cloudflare`** |
| `CF-RAY` | `a32a14aa2c2a8f15-TPE` |
| `set-cookie` | `__cf_bm=…`（Cloudflare bot management） |
| 回應時間 | 0.14 秒 |
| `final_url` | 與請求 URL 相同（無重導） |

**這代表請求根本沒有到達 Dcard 的應用層。** 因此本次驗證：

- **證明了**：以此方式（一般 HTTP client、**自 Docker bridge NAT 經消費級 ISP 出口**，
  **非資料中心**；`CF-RAY` 尾碼 `TPE` 為 Cloudflare 台北邊緣節點）**無法取得** Dcard 資料。
- **沒有證明**：`/service/api/v2/forums/stock/posts` 端點是否仍存在、
  契約 §4.3 的五個欄位是否仍正確。**A3／A4 一次都沒測到。**

換句話說，這是**第三種 FAIL**，§3.3 原本設想的兩種（「端點還在但契約過期」／「端點消失」）
都不是它：**端點是否存在無從得知，因為我們沒被放進門。**

#### 17.2.1 【第四輪更正】原稿寫「資料中心出口」是錯的，而且把結論寫弱了

本節初稿在「**證明了**」那一行寫「資料中心出口」。**這台機器不是資料中心。**
複查指出後核實（`VERIFIED THIS SESSION`）：

| 事實 | 值 |
|------|-----|
| 容器預設路由 | `default via 172.19.0.1 dev eth0`（`172.19.0.0/16`，Docker bridge NAT） |
| 網路模式 | `.devcontainer/docker-compose.yml:19` `network_mode: service:db`，共用 db 容器 netns，仍是 bridge NAT |
| 實際出口 | Docker Desktop → WSL2 → Windows host → **一般消費級 ISP** |
| `CF-RAY` 尾碼 | `TPE`（Cloudflare 台北 PoP，離 client 最近的邊緣節點，與台灣一般網路相符） |

**為什麼這一句非改不可**：它會被抄進 RISK-003 的緩解欄與 DEC。
未來重新評估的人讀到「資料中心出口被擋」，最自然的下一步是「那從一般網路試試看」——
**而那正是本次已經做過的事**。他會再申請一次授權、再跑一次、再拿一個 403。

**而且事實的方向與原稿相反**：一個**台灣消費級 IP** 就被 Cloudflare bot management 擋下，
是「Dcard 廣泛封鎖自動化流量」的**較強**證據，不是較弱。**原稿把自己的結論寫弱了。**

> 這是本輪第二次同型錯誤：把**未經查證的環境假設**寫進「證明了」那一欄。
> 「資料中心」不是我觀察到的，是我以為的。

### 17.3 本次觀察的界限【必須與結論一起被讀到】

### 17.4 對 §4.1 處置的影響——**建議修正一處措辭**

§4.1 第 3 項原訂於契約 §4 加註「**暫停適用——實測 A_n 失敗**」。
依 §17.2，該措辭會讓未來讀者以為端點本身經測不可用。**建議改為明載失敗性質**：

> 本章節暫停適用——`UG-G2-SB5`（2026-08-29）實測 **A1 FAIL（HTTP 403，
> Cloudflare 邊緣攔截，回應為 HTML 挑戰頁而非 API 回應）**。
> **A2–A6 均為 `NOT EXECUTED`，端點是否仍存在、欄位契約是否仍正確，本次未能取得任何證據。**
> Dcard 來源 `DEFERRED WITH EVIDENCE`。章節內容原文保留，供未來重新評估時對照。

**複查要求另加的一句（已採用）**：

> **重新評估的前提不是「再跑一次這支腳本」**——同一條路徑會得到同樣的結果。
> 需要的是下列其一：**Dcard 的邊緣防護政策改變**，或**改採本契約未涵蓋的存取方式**
> （官方 API、認證存取等），而後者需**另行提案與授權**。

沒有這一句，`DEFERRED WITH EVIDENCE` 會被讀成「過陣子再試試」。

同理，RISK-003 的緩解欄應記「**被 Cloudflare 攔截，未觸及應用層**」，
而非只記「API 不可用」——**兩者對未來要不要重新評估的意義完全不同。**
