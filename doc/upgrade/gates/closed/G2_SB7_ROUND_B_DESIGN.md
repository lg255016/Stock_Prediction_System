## 1. 【第一題】`SOURCE_FAILED` 的列：**寫入但標記**，不是不寫入

### 兩個事實讓它幾乎不是選擇

**事實 1：schema 早就為「寫入但標記」設計好了。**
`002_expand_ml_features.sql:86-88` 逐字：

```sql
ADD CONSTRAINT chk_source_status_domain
CHECK (source_status IS NULL OR source_status IN
       ('SUCCESS', 'SUCCESS_EMPTY', 'SOURCE_DEGRADED', 'SOURCE_FAILED'));
```

**四態的 CHECK 已經在資料庫裡。** 若答案是「不寫入」，
**那個約束的後兩格結構上無法到達** —— §9A.1 在資料庫層。

**事實 2：「排除訓練」目前沒有執行者。**

```
grep -rln "daily_ml_features" src/ml/   →  零命中
```

`src/ml/` 從來不讀 `daily_ml_features`；只有 `db_writer.py` 與 `feature_aggregator.py` 讀它。

> ⚠⚠ **所以 SB7 交付不了「該筆排除訓練」，只能交付「讓它可被排除」。**
> **Gate B 不得寫成「契約 §7.4 已實作」——那句話會是假的。**
> 正確措辭：**「標記已實作；排除由 Gate 3 的 panel dataset 執行，尚未存在」**。
>
> `src/ml/panel_dataset.py` 屬 `UG-G3-SB2`。
> **在 Gate 2 的授權下建 Gate 3 的元件，是越界** —— B 輪不做。

### 對照

| | 不寫入 | **寫入但標記（採納）** |
|---|---|---|
| 該列在 DB 裡 | **不存在** | 存在，`source_status = SOURCE_FAILED`、情緒欄 NULL |
| 「那天沒跑」vs「那天失敗」 | **分不出來** | 分得出來 |
| CHECK 的後兩態 | 永遠不可達 | 可達 |
| 與 `label_reason` 的既有慣例 | 相反 | **一致**（值為 NULL 時寫入該列並記成因，不是省略該列） |

> **「不寫入」是同一個病往上升一層**：
> `SUCCESS_EMPTY` 讓「失敗」看起來像「沒資料」；
> **「不寫入」會讓「失敗」看起來像「那天不存在」。**

## 2. 【第二題】分界是「哪一種列」，不是「哪一欄」

### 我第一版的分界錯了

第一版說：「`bullishness_index`／`agreement_index` 屬 RISK-020，不預設一起改。」

**那是把「哪一欄」當成分界。** 複查方 2026-09-04 指出正確的分界是**「哪一種列」**：

契約 `:321` 逐字要求 `SOURCE_FAILED` 時
「**該來源當日特徵保持 `NULL`**；不得寫入 0 或中立值；該筆排除訓練」——
**「該來源當日特徵」涵蓋所有由該來源衍生的欄位，不只 `sentiment_mean`。**

### 條件式分流（採納）

| `source_status` | 處置 | 依據 |
|---|---|---|
| **`SOURCE_FAILED`** | **不填，全部保持 NULL** | 契約 `:321` **強制**，**非** RISK-020 範圍 |
| `SUCCESS_EMPTY` | **維持現行填值**（`0.5`／`0.0`） | **RISK-020 未裁決，不提前動** |
| `SUCCESS` | 不變 | —— |

### ⚠ 涵蓋欄位：**指向 `FEATURE_REGISTRY.md` §5A.3，不複製清單**

> **【2026-09-04 修訂】第一版寫死了五欄，而 §5A.3 列的是八欄。**
> 複查方在上一則給了一份五欄的清單，我照著寫進提案 ——
> **而他隨即自己更正：「我應該指向 §5A.3，而不是寫一份清單。
> 我寫了清單，清單就短了三欄。」**
>
> **這正是本 SB 一路在抓的形狀，這一次的來源是複查方，而我照抄了。**
> **修法不是把五改成八，是不要在這裡放清單。**

**權威來源：`FEATURE_REGISTRY.md` §5A.3 的「社群情緒」群組（該處逐字列 8 欄）。**
本提案**不複製那份清單** —— 若日後契約增列，指標會自動涵蓋，複製的清單不會。

§5A.3 對該群組每一欄的 `SOURCE_FAILED` 規則逐字皆為 **「必須 NULL」**。

⚠ **我第一版漏掉的三欄各有其重要性**：

| 漏掉的欄 | 為何重要 |
|---|---|
| `article_count` | 現為 `fillna(0)`（`:440`）。**在來源失敗的日子，`article_count = 0` 就是「失敗長得像沒資料」本身** —— 它是這條鏈最直接的表現形式，而我漏了它 |
| `sentiment_3d_ma` | 見第 3 節 —— **契約已規定它在 `SOURCE_FAILED` 列必須 NULL** |
| `sentiment_5d_ma` | 同上 |

⚠ **`comment_volume_ratio`／`comment_polarization` 不在本輪範圍**：
§5A.3 同樣標它們「必須 NULL」，**但它們的填補策略本來就是「不填補 — 保持 NULL」**，
**已經合規**。列出來是為了說明本輪的範圍邊界是查證過的，不是猜的。

**這樣同時滿足三件事**：契約 `:321` 被遵守、RISK-020 不被提前裁決、
**兩個 NULL 成因不會塌成同一個表示**。

> ⚠ **若整段移除 `fillna`，`sentiment_mean` 為 NULL 會有兩個成因**
> （來源失敗／那天真的沒文章），**而兩者都是 NULL 就分不出來了** ——
> **那正是這條鏈一路在修的病。**

### `sentiment_lag_1/2` 自帶 `fillna`，必須一起改

`feature_aggregator.py:560-561`：

```python
df_features['sentiment_lag_1'] = df_features.groupby('stock_id')['sentiment_mean'].shift(1).fillna(0.5)
df_features['sentiment_lag_2'] = df_features.groupby('stock_id')['sentiment_mean'].shift(2).fillna(0.5)
```

**只改 `:441` 不夠——那兩行會把 NULL 再填回中立值。**
（實測：`shift(1)` 本身**會**產生 NaN，隨後被 `fillna(0.5)` 蓋掉。）

## 3. 【第三題】移動平均：**(b) 押後，本輪做 (c) 的文件部分**

### 問題（複查方 2026-09-04 發現，PM 第一版漏了）

我第一版把 `sentiment_3d_ma`／`sentiment_5d_ma` 列進「會出現 NULL」的欄位。**那是錯的。**

`:554-556` 用的是 `rolling(window, min_periods=1)`，而 **pandas 的 rolling 預設跳過 NaN**。
實測：

```
sentiment_mean : [0.6, 0.7, NaN, 0.8, NaN]
min_periods=1  : [0.60, 0.65, 0.65, 0.75, 0.80]   ← 第 3 列不是 NaN
min_periods=3  : [None, None, None, None, None]
```

> **所以在一個「來源失敗、我們對情緒一無所知」的日子，
> `sentiment_3d_ma` 仍然會有值 —— 而那個值是從別的日子推出來的。**

**這比它取代的東西更難發現**：今天 `sentiment_mean` 是偽造的 `0.5`，MA 平均進去也是 `0.5`
——**顯然錯，但一眼看得出是常數**。
**若只移除 `fillna`，MA 會變成一個由真實鄰近日推出的、看起來合理的數字** ——
**偽造訊號沒有消失，只是變得更像真的。**

### ⚠ 先釐清：**`SOURCE_FAILED` 列上的 MA 必須 NULL，那是契約不是選項**

> **【2026-09-04 修訂，複查方指出】**
> `FEATURE_REGISTRY.md` §5A.3 對 `sentiment_3d_ma / sentiment_5d_ma` 的
> `SOURCE_FAILED` 規則逐字是 **「必須 NULL」**。
>
> **所以那件事不是本輪的設計選擇，是已核准契約。而它不需要任何新欄位。**

**(b)／(c) 的爭論範圍因此比第一版小得多，只剩一個殘餘問題**：

> 某一列**自身那天正常**，但它的 MA 窗內**含有一個失敗日** ——
> 此時 MA 會靜默地少算幾天，而沒有任何標記。

**那是真的，但與 `SOURCE_FAILED` 列無關** —— 那些列已由契約要求 NULL。

### 三個選項與量測（僅針對上述殘餘問題）

| 選項 | 內容 | 對現有 117 列的影響（**實測**） |
|---|---|---|
| **(a)** | `min_periods=window` | **3d MA 有 8 列變 NULL、5d MA 有 16 列變 NULL** —— **而那些列一次來源失敗都沒有** |
| **(b)** | 維持 `min_periods=1`，**另存「窗內實際觀測日數」** | 現有列的值不變；新增兩欄 |
| (c) | 維持現狀，只在欄位契約寫明「本欄為可得觀測的平均」 | 零程式碼變更 |

**(a) 的量測是決定性的**（`daily_ml_features` 117 列，`SUCCESS` 37／`SUCCESS_EMPTY` 80，
`sentiment_mean` 目前 NULL 0 列）：

```
window=3｜現行 NULL 0 列｜選項(a) NULL 8 列（暖機期）
window=5｜現行 NULL 0 列｜選項(a) NULL 16 列（暖機期）
```

> **那 16 列（13.7%）與來源失敗完全無關 —— 它們是暖機期。**
> **(a) 用「窗不完整就不給值」處理了一個它不打算處理的問題**：
> 暖機期不完整是**時間序列的本質**，不是資料品質問題。
> 而 RISK-020 正是在處理「暖機期填補」那一類，**(a) 會與它撞在一起**。

> **【2026-09-04 修訂】第一版在此否決 (c)，那個否決已不成立** ——
> 理由見下方「我第一版否決 (c) 的理由，被契約解掉了」。
> **保留原文的位置以記錄判斷如何改變，但結論以下方為準。**

### 裁決：**(b) 押後，本輪做 (c) 的文件部分**

> **【2026-09-04 修訂】第一版主張採 (b)。複查方裁決押後，四個理由我逐項核過。**

| # | 理由 | 我的查證 |
|---|------|---------|
| 1 | **`len(contract) == 29` 硬編碼在 contract-check 的 B1** | `gate0_contract_check.py:68` `check("B1", "29 欄契約完整性", len(contract) == 29, ...)`；`:163` `AUTHORITATIVE_COLUMNS = 29`。**加兩欄會讓 B1 直接 FAIL** |
| 2 | **「29 欄」的引用規模** | 實測 `FEATURE_REGISTRY.md` **7 處**、`SYSTEM_UPGRADE_MASTER_PLAN.md` **22 處**，合計 **29 處**（複查方估 28，實測 29）。**比 §0.5 #5 的「24 個 Small Batch」大一個數量級** |
| 3 | **⚠ 那兩份都是 Gate 0 已核准交付物** | 依 `CLAUDE.md` §0.2，其位階**高於** Gate A 提案。**在 SB7 的授權下改 29 欄契約是越界** —— 與「在 Gate 2 的授權下建 Gate 3 的元件」同型 |
| 4 | **方法上的理由（最重要）** | **`SOURCE_FAILED` 到今天為止是不可達的**（那正是本輪要修的）。**所以「窗內含失敗日」的發生頻率現在是零觀測。** 在頻率未知時決定要不要為它加兩個欄位，**是先寫一個數字再拿它當判準** |

**第 4 個理由是決定性的**：(b) 的價值取決於那個殘餘問題發生得多頻繁，
而**那個頻率在 `SOURCE_FAILED` 可達之前無法觀測**。
**押後不是拖延，是等一個現在不存在的輸入。**

### 我第一版否決 (c) 的理由，被契約解掉了

第一版寫：「一個『本欄為可得觀測的平均』的宣告，**不會讓任何人在讀到 `0.65` 時
知道那天其實沒有資料**。」

**那個顧慮成立，但它已經被契約的「必須 NULL」解決了** ——
**在來源失敗的那天，MA 會是 NULL，不是 `0.65`。**

**(c) 剩下要文件化的只有「窗可能不完整」，那確實是文件層級的事。**

### 本輪對 (c) 的具體交付

在 `feature_aggregator.py` 的 MA 計算處加註：
**「本欄為窗內*可得觀測*的平均，非完整窗的平均；窗內若含 `SOURCE_FAILED` 日，
該日不參與計算且本欄不標記此事」**，並登記為具名的已知限制，
**排入 `SOURCE_FAILED` 在生產中被觀測過之後重新評估**。

⚠ **`_obs` 兩欄不新增**（第一版的方案），故 **29 欄契約不變、migration 008 不需要**。
