## 0. 本項會動到 RISK-015 正在等的東西

**現行**：`scrape_ptt_stock_by_keyword(keyword, max_pages=1)` —— 逐關鍵字搜尋。
**本項**：抓看板固定頁面，再在記憶體裡比對關鍵字。

| | 逐關鍵字搜尋 | 固定頁面 + 記憶體比對 |
|---|---|---|
| 涵蓋範圍 | 搜尋索引可及的貼文 | **只有取回的那幾頁** |
| 冷門標的 | 可能找到較舊的貼文 | **可能一篇都沒有 → `SUCCESS_EMPTY`** |
| 熱門標的 | 逐一搜尋 | 一次抓取即涵蓋多個關鍵字 |

**而 RISK-015 的量測依據逐字就是 `source_status` 的「逐股票、逐交易日覆蓋率計算」。**

> **改變取數模式會改變 `SUCCESS`／`SUCCESS_EMPTY` 的分佈**
> —— **也就是改變 RISK-015 要量的那個東西本身。**
>
> **與決策點 2 同一形狀**（不把 150 檔灌進 `stock_prices`，以免在量測前放大分母），
> 差別在那次動的是**分母**，這次動的是**分子**。

**不因此押後**：RISK-015 排在 Gate 3 啟動前，SB7 在 Gate 2 ——
**押到 RISK-015 之後等於把 Gate 2 的交付延到 Gate 3。**
**正解是：不擋，但讓兩個時期可以被分辨**（§2、§3）。

⚠ **涵蓋範圍的措辭**：對冷門標的，本項**很可能使涵蓋範圍下降**。
**本提案寫「下降」，不寫「改變」** —— 後者把一個有方向的後果講成中性的。
下降的幅度**現在無法預估**（見 §3 的量測設計），但方向是可預期的。

## 2. 【條件 2】`source` 的值必須跟著改 —— **三個條件裡唯一補不回來的**

### 先例是本專案自己的

> `source` 用 `'tpex_daily_quotes'` 而不是 `'tpex'` ——
> **來源標記要指向「哪一份報表」，不是「哪個機構」，否則日後換報表就分不出來。**

**逐關鍵字搜尋與固定頁面抓取，是兩份不同的「報表」。**

若兩者都寫 `'ptt_stock'`，**日後沒有任何欄位能分辨某一列來自哪個模式** ——
**那正是 `stock_prices` 沒有 `source` 欄所造成的 RISK-022 面向一，換一個對象。**

> **這一項是「現在不做、日後永遠補不回來」的**：
> 資料一旦寫下去而沒有模式標記，**那個區別就消失了**。
> 條件 1 是量測、條件 3 是紀律，**兩者事後都還能補；本項不行。**

### 提案的命名

| 模式 | `source` 值 | 長度 |
|---|---|---|
| 逐關鍵字搜尋（**現行，將退役**） | `ptt_keyword_search` | 18 ≤ 20 ✔ |
| 固定頁面 + 記憶體比對（**本項新增**） | `ptt_board_pages` | 15 ≤ 20 ✔ |

**兩者皆在 `VARCHAR(20)` 內，不需 migration。**

### ⚠ 既有 331 列的歸屬 —— **不回填改寫，只寫下事實**

既有 331 列全部是 `'ptt_stock'`，而它們**全部來自逐關鍵字搜尋**
（該模式是本專案唯一存在過的 PTT 取數方式）。

**兩個選項**：

| | (a) 回填為 `ptt_keyword_search` | (b) **保留 `ptt_stock`，在文件記明其歸屬** |
|---|---|---|
| 事後可分辨 | 是 | 是（`ptt_stock` ⟺ 舊模式，一對一） |
| 改寫既有資料 | **是** | 否 |
| 風險 | 一次 UPDATE 331 列，且**改寫的是歷史事實的標籤** | 需要有人讀到那份說明 |

**本提案採 (b)**，理由：`'ptt_stock'` 這個值**在切換之後不會再被寫入**，
因此它與 `ptt_keyword_search` 在資訊量上等價（**都唯一對應舊模式**），
而 (a) 要為此改寫 331 列既有資料。

> **「值不好看」不是改寫歷史資料的理由。**
> 需要的是「能分辨」，而 (b) 已經滿足。

⚠ **但 (b) 的代價要明講**：`ptt_stock` 這個名字**不會自己說出它是哪個模式** ——
它依賴一份文件。故 §5 的驗證要求把三個值的對應關係**寫進 `MULTI_SOURCE_DATA_CONTRACT.md`**，
而不只寫在本提案裡（**本提案通過 Gate B 後會移入 `closed/`**）。

## 3. 【條件 1】切換前後各量一次 `source_status` 分佈

**兩份都落檔**，成本接近零 —— B 輪的驗證已經在查這個分佈（37／80／0），同一句 SQL。

```sql
SELECT source_status, count(*) AS rows,
       count(DISTINCT stock_id) AS stocks,
       count(DISTINCT trade_date) AS days
FROM daily_ml_features GROUP BY source_status ORDER BY source_status;
```

| 時點 | 檔名 |
|---|---|
| 切換**前** | `evidence/G2_SB7_item5_coverage_before.json` |
| 切換**後**（首次以新模式執行之後） | `evidence/G2_SB7_item5_coverage_after.json` |

> **RISK-015 屆時看到的資料橫跨兩個取數模式。**
> **有這兩份，它知道斷點在哪；沒有，它會把模式差異讀成覆蓋率變化。**

⚠ **誠實的限制**：切換後的量測**要等新模式實際執行過**，
而 `run_all_daily_tasks` 的真實執行**仍暫緩**（理由：呼叫 Gemini API + 重算特徵）。
**所以「切換後」那一份在本 SB 內可能取不到。**

**若取不到，Gate B 必須寫成「切換前已量測；切換後待首次生產執行」，
不得只放一份就宣稱「已量測分佈變化」。**

## 4. 【條件 3】請求量與 DEC-032 紀律

### 4a. 每日請求數 —— **我無法從現有資料推導頁數，這一點要先說**

**本專案從未抓過看板索引頁**，只抓過搜尋結果。
因此「一天的貼文需要幾頁」**沒有任何可用的觀測**。

> **在沒有觀測時給一個頁數，就是先寫一個數字再拿它當判準** ——
> 那正是 C7 註記與 K 值校準都反對的做法。

**故本提案不宣稱頁數，而是設一個預算與一條規則**（比照 SB9 的 `REQUEST_BUDGET`）：

| # | 規則 |
|---|------|
| 1 | **每日請求預算 = 25**（與現行模式相同，**不增加**） |
| 2 | 由最新一頁往回抓，**直到取回的貼文最舊時間早於「上次執行的最新貼文時間」**即停止 |
| 3 | **預算用盡仍未回溯到該時間點 → 停止並記為 `SOURCE_DEGRADED`**，不自行加碼 |
| 4 | 首次執行無「上次時間」→ 抓 **1 頁**，並記明這是首次 |

**規則 1 的推導**：現行是 25 個關鍵字 × 1 頁 = 25 個請求。
**取相同的數字作為上界，使本項在請求量上「至多不惡化」** ——
而規則 2 使實際用量預期**遠低於**上界（一天的貼文通常不需要 25 頁）。

> **這不是「25 頁是對的」，是「25 是我們已經在用的量，不因換模式而增加」。**
> 實際需要幾頁**由首次執行量出來**，Gate B 回報實測值。

⚠ **規則 3 讓 `SOURCE_DEGRADED` 第一次有了可達路徑** ——
B 輪的已知限制「該態需要逐頁 outcome 而 scraper 不回報」在本項會被解掉。
**但本提案不宣稱它已可達，那要等實作與測試。**

### 4b. DEC-032

`ptt_scraper._fetch_page` 已於 `0047d98` 加上 `retry=` 條件（403／429 硬停）。
**新路徑必須走同一個 `_fetch_page`，不得另開一條 HTTP 入口。**
釘住它的驗證見 §5。

### 4c. 內頁回填不變

`backfill_ptt_comment_counts` 的請求數與本項無關（每個**新** URL 一次）。
⚠ 但見 §1 的附帶發現：**該回填目前一列都沒成功過**，
故現行的內頁請求**實際上沒有產生資料**。**本項不處理，但 Gate B 要記。**
